# OpenSpec, HLV and AI Factory/AIFHub handoff

This is an explicit optional workflow example; native application checks are independent. No workflow tool or extension is installed by verification.

1. The requirements source is [OpenSpec planner specification](openspec/specs/planner/spec.md). With OpenSpec 1.15.0 provisioned, run `openspec validate --specs --strict --json --no-interactive` from this `planner-shared` directory. OpenSpec owns requirement text, not application implementation.
2. Run the common real HTTP/PostgreSQL conformance command from the repository root as described in [the quickstart](../README.md). Preserve its exit status and full report with the exact source revision. HLV consumes actual native results; do not label a configured gate as a passed gate.
3. For an isolated HLV 1.0.0 adoption exercise, export an example, then run `hlv init --adopt --project planner-reference --owner reference-maintainers --agent codex --profile minimal --path <exported-project>`. This CLI also asks milestone/policy preferences: answer them explicitly for the new exercise. It owns its `.hlv/` configuration and validation receipts. Attach the OpenSpec requirement IDs, shared scenario IDs and the real conformance command through the generated HLV contracts/gates. `hlv check --root <exported-project>` checks those artifacts; acceptance requires actual native gate execution separately. Initialization alone is not application or HLV-gate PASS.
4. [The AI Factory extension descriptor](ai-factory-extension.json) configures the existing read-only Lekalo MCP server. In the exported project's workflow installation, an AIFHub Extension may consume the schema-defined neutral trace manifest described in [trace-manifest.md](../../docs/trace-manifest.md), preserving the OpenSpec/HLV external IDs. This example does not register global extensions or silently initialize this repository.

Authority chain: OpenSpec requirement → shared Lekalo semantic symbol → maintained Node/PHP implementation → common native scenario → actual HLV/native receipt → AIFHub workflow consumption. Linking configuration and requirement IDs is distinct from proving execution. The caller must carry source revision, model digest and actual evidence digests into any exported trace; no placeholder PASS receipts are committed.

The existing bounded ownership exercises are executable demonstrations:

- Observed: [synthetic brownfield tutorial](../../docs/tutorial-brownfield-typescript.md); scanning records derived evidence and never makes code generator-owned.
- Contracted: from the repository root, `node scripts/test-reference-contract.mjs` exports the actual Node and Laravel references and records eight owner-declared file-level semantic bindings per target. It proves missing-coverage refusal, explicit native-test attachment, clean declared signature/effect conformance and fingerprint drift refusal without rewriting maintained code. `nativeCoverage` in `reference-matrix.json` maps those bindings to real test IDs emitted by the HTTP gate. Attaching a test ID records coverage presence; the separate HTTP/PostgreSQL run proves execution. [Contract one module](../../docs/adoption.md#contract-one-module) explains the same primitives interactively.
- Managed: from the repository root, `node scripts/test-managed-planner-e2e.mjs`; it deletes and regenerates only admitted support-code outputs and compares the retained canonical inputs across roots. This does not generate the entire maintained HTTP/PostgreSQL applications.

The observed and managed exercises retain their existing fixture scopes; the contracted exercise uses the actual shared reference model and maintained application sources. The new HTTP corpus supplies runtime evidence, not automatic promotion into a supported generated capability. See `reference-matrix.json` for the exact maintained HTTP profile and deferred Go/Rust targets.
