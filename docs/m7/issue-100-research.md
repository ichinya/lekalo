## Proposed task protocol and harness neutrality

### Arms, resource equality and experiment unit

One experiment unit is `(pilot, taskVersion, fixtureDigest, baseRevision, executorProfileDigest, modelProviderProfileDigest, repetitionIndex)`, with exactly two independent runs, A and B. Each task starts from its own approved baseline; changes from a previous task do not carry forward. Fresh processes, conversation state, filesystem copies and isolated database seeds prevent learning/state carryover. Counterbalance A/B order within repetition blocks and record the randomization schedule/seed before execution; pairing controls scheduling variation, not identical LLM randomness. Record a model seed only if the provider supports it, including whether it was honored.

Use the same external agent executor, terminal/read/search/edit tools, context/output caps, timeouts, retry policy, prompt wrapper, native package versions, machine resources and hard verifier for both arms. The executor must run A without invoking the Lekalo binary or libraries; no generated Lekalo context is inserted into A's prompt. B's approved tool-policy difference enables Lekalo operations and exposes its semantic attachments. Both receive the identical natural-language change request, ordinary framework documentation snapshot and behavioral acceptance requirements. B receives no authored solution patch, future baseline or hidden oracle answers.

Application/native-source bytes, data seed, dependency locks and revision are identical across arms. Existing generated application code remains identical and usable in A: this primary experiment measures **change-workflow assistance on a matched starting application**, not the causal benefit of constructing that application from scratch. The same baseline contains the semantic attachments, but A's isolated read view excludes those attachments, their capsules/caches, Lekalo-specific instruction files and tools; B exposes them. Record the application tree digest separately from semantic bundle and arm read-view/tool-policy digests. The intentional exposure difference is explicit treatment provenance, not an excuse for different source fixtures. A separate ordinary-handwritten-application experiment would need its own campaign and comparability rationale.

For greenfield contracted tasks, B may update declarations and use admitted generation as part of the workflow, with that time/tokens/tool activity charged. Primary acceptance is shared native behavior and regression checks for both arms. B's contracted conformance has its own reported disposition and required B treatment-integrity check; A is not failed for lacking a Model. Agent edits cannot alter the protected verifier, task protocol, expected values, schedule, or baseline. Semantic metadata maintenance and generated/maintained source churn are reported separately alongside total churn.

For brownfield observed tasks, B can adopt/scan/bind and use inspect/impact/context on an isolated copy; existing untouched code remains observed. Include cold setup/scan/binding costs in primary end-to-end measurements. A warm-index companion result is a separate preregistered stratum with index source digest/freshness, not a replacement for cold results. No rewrite or promotion of legacy into contracted mode is necessary. Both arms perform the same scoped change; post-change full native checks and an evaluator-owned affected-surface set assess the consequences. A emits its exploration/impact answer through the neutral task format; B's impact answer uses that same format, so coverage can be compared without requiring A to call Lekalo.

**Executor gap:** the repository's pilot/scenario/doc harnesses execute fixed recipes, not an instrumented model executor. A neutral executor with complete tool/read/usage events, provider adapters and independent verification is new work. Do not call today's `test-pilot-laravel-vue.mjs` or `history record` the standard agent workflow. Provision dependencies visibly before the run; installation is not hidden inside a measured verification leg. Pin its inclusion/exclusion from latency/cost before the campaign.

### Metric definitions, sources and deterministic availability

Proposed result metrics use `known/unknown/withheld/unsupported`; only known carries a typed value. Missing instrumentation is unknown, unavailable capability unsupported, deliberate privacy suppression withheld. An undefined ratio uses `state: unknown` with a closed reason such as `no-success` or `zero-denominator`, not a fifth numeric state or infinity. Zero is known only when measured. Every known metric binds source component/version, source event/receipt digest and measurement recipe. Counts/decimals cannot be mixed with prose estimates. ## Proposed verified-success and failure classification

The verifier is outside both agents' writable trees and recomputes candidate digest before and after checks. It runs the same current native behavior/regression suite, identifies every required assertion, validates coverage and classifies failures. B additionally supplies current contracted conformance or observed integrity receipts; those are not substitute native assertions. Preserve raw source outcomes, mapped evaluation status and reason class as separate fields.

Reuse reference traces only for supported semantic assertions; reuse actual Node/Laratesto scenario-run rows and native gate receipts for executed native behavior. `verify_with_components` can expose component/assertion evidence with current IR/expected tests, but its optional capability defaults do not meet the task's mandatory-oracle requirement. A missing native receipt, stale IR/test binding, unsupported authorization/race assertion, missing expected test, failed assertion, blocked/security receipt or incomplete suite prevents verified success. A provider's "done" message, compilation alone, green ingestion or 10/10 judge score never overrides this rule.

| Proposed failure class | Classification evidence and accounting |
| --- | --- |
| `task` | Executed required assertion fails, wrong implementation, undeclared/unrelated forbidden mutation, model refusal of an in-scope authorized task, or consumed agent resource cap. Count as no verified success; keep all tokens/cost and failed assertions. A test failing because the agent broke SQL is a task failure. |
| `provider` | Auth/quota/rate/service availability/transport failure or provider-side termination before usable completion, supported by request/attempt metadata. Preserve all charged attempts. Retry only the fixed policy; do not call an assertion failure a provider outage. Content-policy refusal is recorded distinctly from transient transport failure. |
| `infrastructure` | Independent provisioner/verifier/tool spawn failure, unavailable database/service, host crash or confinement infrastructure failure not caused by candidate behavior. Store failing stage/source outcome and include known wasted cost/time. |
| `unsupported` | Task oracle/executor/provider instrumentation capability not available for the frozen protocol. Required capability preflight stops scheduling that stratum; a later discovered gap remains an incomplete attempt, not task success. |
| `custody-security` | Altered oracle/baseline, unapproved model fallback, invalid receipt binding, private egress or execution-policy violation. Invalidates verified acceptance and claim eligibility; retain locally classified evidence. Never reduce this to an ordinary passing gate plus warning. |
| `interrupted` / `not-started` | User cancellation, lost run or preflight failure; visible schedule row with stage and known cost, no fabricated usage/latency/pass. Later completion is a linked attempt. |

Multiple classes can coexist: keep all witnessed failures and apply a frozen precedence for primary presentation (`custody-security`, executed task failure, provider, infrastructure, unsupported, interruption). An observed hard regression cannot disappear when a provider fails later. Failure classification requires evidence; absence of a complete provider/infra ledger remains unknown.

## Proposed baseline immutability and determinism strategy

An approved baseline binds application tree, data seed, semantic bundle, dependencies, task/oracle/holdout digests, executor and profiles, measurement recipe and analysis schedule. Separate fixture correctness approval from experimental outcomes. Approval references the exact complete digest tuple and approver role/date; a digest alone proves byte identity, not approval/authenticity. For public synthetic data, commit the content and manifest, reference the immutable Git commit/tree plus digest, and use a reviewed approval sidecar outside self-hashed content. For private data, keep a local access-controlled content-addressed archive with opaque public alias and local approval; private content/path digests stay local.

No runner overwrites a baseline/report or follows a mutable "latest" pointer without a resolved digest. Drift in any approved pin fails before provider launch. A change uses a new baseline version/ref with an explicit comparison reason and new campaign, leaving prior content/results intact. Agent trees are disposable copies with protected oracle views; assert original/approved bytes unchanged after execution. DB isolation uses a fresh namespace/seed for each arm/attempt and a frozen cleanup receipt, not shared writable state.

#75 immutable input baselines and #77 `baselineReadyRef` are useful conventions but do not implement campaign approval/storage. #121 also permits retention/deletion. Register local result claims as dependent references and resolve them against live digest-bound records before reporting; invalidated/pruned history references invalidate live claims. Approved evidence needs explicit local retention/archive policy outside the recorder's default pruning window. Archival approval is not permission to resurrect a deleted private record or keep private backups against deletion policy; withdrawal produces a tombstoned/ineligible claim rather than an invented surviving proof. #102 must decide how any admitted public projection reconciles retention/withdrawal.

Separate deterministic **replay of recorded evidence** from nondeterministic **rerunning the agent**. Canonical UTF-8 JSON uses stable key order, explicit semantic row order, bounded values and one trailing LF; content digests exclude only fields explicitly outside the content identity (approval sidecar and digest itself). Validate ratios, sums, population reconciliation and candidate/assertion joins independently of producer arithmetic. Do not hash private paths into public identities. Runtime timestamps/IDs stay outside byte-equality expectations for stable metric projections; full provenance preserves actual run timestamps.

## Proposed statistical analysis and negative-result guarantee

Report each pilot/task/model/provider/executor/profile stratum separately. Primary success rate is verified successes divided by all preregistered scheduled arm slots (intent-to-run); rows never started, interrupted or provider/infra incomplete have no demonstrated success but remain visibly classified, rather than asserted to be behavioral failures. Also report started/completed/eligible counts and a secondary task-conditional rate excluding preregistered provider/infra-only cases with the exact exclusions. Preserve paired availability; an incomplete partner is not silently dropped from primary totals. Explain attrition and show worst/best bounds for unknown outcomes.

Define lift as `p_B - p_A` in percentage points; publish both arm numerators/denominators. For matched complete pairs, report discordant outcomes and a preregistered paired interval/test method; do not treat paired observations as independent samples. Proposed small-pilot uncertainty: exact paired success inference with counts, Wilson intervals for displayed marginal rates, and a seeded paired bootstrap for continuous deltas/ratios, all with versioned analysis recipe and explicit 95% interval label. Bootstrap within task/stratum; do not pool repetitions into an invented number of independent repositories. When task/repository breadth is too small, show descriptive intervals and label scope instead of asserting population generalization.

Report cost/token/tool/iteration/context metrics for all attempts and successful attempts separately to expose survivor bias. Primary `cost_per_success` includes all known campaign attempt costs, including provider/infra waste, and reports cost coverage. A secondary task-conditional cost ratio names exactly excluded costs and successes. Show mean/median, spread, sample counts, paired B-minus-A deltas and uncertainty; ratios with zero baseline/no successes are undefined with reason. Timeout latency is censored; report completion probability and censored fraction, not a fast median after discarding timeouts. Partial pricing or usage produces an unknown total with known subtotal, never a fabricated exact average.

Preregister practical-equivalence bounds, primary endpoint (verified success), secondary metrics, repeat count and stop rules. The initial ten-pair/task pilot is descriptive. Exploratory metrics/profile sweeps are labeled and their multiplicity is visible; do not select whichever token or success metric looks best. Empirical context-budget calibration needs a separate randomized budget sweep and complete task oracle; a single successful capsule does not turn #75's `empiricallySafeContextTokens` into a general threshold or justify changing its contract.

**Honest negative-result guarantee:** emit a row for every scheduled task/arm/repetition, including failures, neutral/worse B results, incomplete/censored runs, and all interventions. Freeze the schedule and analysis before outcomes; publish aggregate count reconciliation and immutable result refs. No retry replacement, dropped failed task, judge override, retrospective task simplification, profile switch or best-run cherry-picking. If B lowers tokens but harms verified success, show both outcomes without declaring overall superiority. Negative/neutral reports use the same evidence/status format and retention rules as positive reports. Conclusions are limited to the tested tasks, fixture/repository alias, model/provider/runtime/profile/version and sample size; no universal superiority claim from one model or repository.

### Research validation boundary

This phase used read-only Git/source/schema inspection and live issue/dependency reads. It verified product/registry counts, current local integration SHA, fixture distinctions and current metric field vocabularies. An in-memory document audit found all ten main sections, all nine distinct AC mappings and all twelve required metric categories; all non-wildcard expanded inventory paths resolved, and the one illustrative JSON fragment parsed. Whitespace and the staged/committed single-file boundary are checked before delivery.

## Risks

- **Treatment contamination:** starting generated code may already embody Lekalo decisions; label the matched change-workflow question. Different application snapshots, hidden solution artifacts or A exposed to B context destroy the intended comparison.
- **Missing telemetry:** history stores observations but cannot recover unlogged files/tool calls/replans/cache billing. Report incomplete coverage; structural chars-4 estimates cannot fill provider usage gaps.
- **False acceptance:** optional unsupported execution in `verify`, authored scanner stubs, fake HTTP repositories and semantic event intents can all look reassuring while native behavior remains untested. Required independent assertions and mutation controls are essential.
- **Sampling and attrition:** ten repeats over a few tasks/model profiles do not imply repository breadth or universal lift. Provider outages, censoring, survivor-only cost and optional stopping can reverse a reported conclusion.
- **Profile confounding:** #84 is pending. Architecture adoption and semantic tool assistance need separately named treatments and visible baseline/profile changes; an existing budget profile cannot stand in for `ai-strict`.
- **Privacy and publication:** path hashes, raw receipts/prompts, detailed private digests, fine-grained sizes and debug logs can leak identities. #119 does not police an arbitrary executor's network; #102/AIFHub public admission remains future work.
- **Custody and retention:** a closed schema, hash, local ingestion receipt or immutable filename does not prove honest execution/approval. History pruning invalidates claims; preserve and withdraw approved evidence according to its actual local custody policy.
- **Task realism:** priority already ships in the MySQL fixture; relation extraction and concurrency need genuine approved starting conditions and additional native oracles. Do not turn a no-op or unsupported task into positive benchmark evidence.
