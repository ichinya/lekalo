## Proposed command/report schema and ownership

### Proposed ownership and artifact decision

**Proposal:** core owns language-neutral rule meaning, applicability, evidence qualification, profile resolution, comparisons and verdicts in `crates/lekalo-core/src/architecture_profile/`. CLI owns bounded classified reads, project/module selection, adapter dispatch through existing transport and output in `crates/lekalo-cli/src/architecture_profile.rs`. PHP/Node and future adapters own native rule mapping, collector recipes, framework distinctions and toolchain compatibility. Existing validator/AI-lint/coupling/context-budget/error/contracted/trace services remain the producers and authorities for their facts.

**Proposal:** publish these closed Draft 2020-12 families at `<V>`: `architecture-rule-catalog.schema`, its core catalog instance, `architecture-profile.schema`, the four named built-in profile instances, `architecture-profile-report.schema`, `architecture-profile-diff.schema`, and `architecture-adoption.schema`. Target catalogs use the same catalog schema with an exact adapter owner/namespace and version/digest pin. A registry diagnostic ID is not an architecture catalog ID: one architecture requirement may need several producer checks, and several requirements may reuse one finding. Keep an explicit many-to-many map and deduplicate report/diagnostic projection by original producer finding identity.

**Proposal decision:** do **not** extend the current validation-profile fields or rename its built-in `strict` to `ai-strict`. That schema is project-only and its parser deliberately prohibits upgrades; extending it would couple numeric metrics, required target evidence, adoption, inheritance and generation custody to semantic validation. A separate architecture document can compose those concerns with exact typed references while semantic profile decoding remains unchanged. Reusing target-profile would confuse capability composition with architecture obligations; merging coupling or lint schemas would give one service ownership over another's measurements. New published families are justified; duplicate measurement engines are not.

**Proposal:** use one authoritative authored catalog of rule recipes/rationales/alternatives, with a deterministic generator producing schemas, built-ins and machine inventory; Rust uses closed typed decoding and explicit dispatch to producer APIs. Generated metadata must be checked against registered diagnostics and decoder enums. A generator cannot be the sole acceptance oracle for its own calculations. Existing independently authored goldens and hostile runtime inputs remain necessary.

### Proposed catalog schema

**Proposal document:** `{schemaVersion, identity, catalogId, catalogVersion, owner, rules}`. `owner` is a closed core-or-adapter union; an adapter owner includes ID/version/artifact digest/protocol and target-profile pins. A rule contains `{id, revision, lifecycle, domain, applicability, producerChecks, measurements, requiredEvidence, defaultSeverity, minimumSeverity, mandatory, rationale, alternatives, blockingBasis, comparisonRecipe}`. References are exact identity/version/digest triples; no ranges, mutable URLs, runtime plugins or arbitrary nested metadata.

**Proposal semantics:** stable dotted IDs name requirements, integer revisions name a frozen recipe, lifecycle records active/deprecated/replaced with an exact successor link. Changing meaning allocates a new rule or explicit recipe revision, never silently reuses an ID. Core IDs below are `architecture.*`; target rules use adapter-owned namespace prefixes and cannot redefine core rules. Producer checks name registered diagnostic IDs, service/recipe and declared result semantics, including clean coverage. Measurement references name existing closed metric keys and units, not executable expressions. Applicability explicitly distinguishes semantic/observed/native/generated subjects and unsupported target features.

**Proposal evidence slot:** `{kind, schemaRef, producerRef, coverage, currency, minimumConfidence, claim}` with complete/partial/unknown/unsupported/withheld coverage and exact/high/medium/low/unknown confidence kept separate. Structural identity is not verified execution. An adapter capability claim is insufficient evidence that every scoped subject was inspected. Negative findings require an independently recorded complete recipe/eligible-subject inventory; absent records do not mean clean.

**Proposal blocking admission:** `blockingBasis` is a closed semantic-invariant or measured-threshold union. A threshold names metric/recipe/unit/completeness, comparator and calibration/review ref; all subjective advice has no blocking basis. Rationale explains how a finding impedes local understanding or change safety; alternatives specify a concrete boundary/declaration/tracking action and prerequisites. Default messages stay English and bounded. Catalog prose does not authorize source mutation or native commands.

### Proposed profile and resolved report

**Proposal profile document:** `{schemaVersion, identity, catalogRefs, profiles, assignments}`. Each profile is `{id, profileVersion, extends, ruleChanges, serviceRefs, adoptionRef}`. IDs are the four exact built-in names or a namespaced consumer extension; versions are exact canonical versions. `extends` is an explicit none-or-pinned-parent union. `ruleChanges` is a sorted unique list keyed by catalog rule ID with enabled, severity, evidence requirements and gate participation; entries can only select catalog-supported policies. `serviceRefs` is a closed union of exact semantic/lint/coupling/context-budget/contracted/trace/adapter config references. Keep referenced bytes and normalized effective values/digests separate; profile name is never a substitute for content identity.

**Proposal resolution report:** `{schemaVersion, identity, scope, pins, inheritance, effectiveRules, serviceSelections, coverage, findings, adoptionAudit, measurements, assessment}`. Pins include catalog/registry/profile source and resolved digests, every parent, assignment policy, Model/IR/observed/source manifest, target/capability/tool/adapter, service configs and reports, baseline/adoption and explicit evaluation date if used. Findings include architecture rule/revision, original producer rule/finding, exact subject, target, scope, rationale, alternative, witness/evidence/location refs, claim/confidence/currency, raw severity, effective severity, gate disposition and adoption disposition. Preserve rich producer reports by digest/reference rather than stuffing unbounded evidence into diagnostic data.

**Proposal:** resolve/read-only inspect first, then assess explicitly selected subjects using current admitted evidence. No target execution, dependency install, baseline authoring or artifact generation occurs implicitly. Denied results retain resolved policy, raw findings and debt audit. Unsupported required evidence can deny the selected policy, but the report must say evidence gap, not proven architectural violation. Invalid documents/joins refuse before a "passed" assessment can exist. Use current DomainResult conventions: advisory valid/0, malformed invalid/1, explicit policy denied/3, wholly unsupported operation/4 or version/5 as appropriate; registry status allowlists must be tested independently.

Illustrative **proposed CLI grammar**, deliberately distinct from current `--profiles` meanings:

```text
lekalo architecture-profile resolve --architecture-profiles FILE --architecture-profile ID --profile-version VERSION --project DIR
lekalo architecture-profile assess --architecture-profiles FILE --architecture-profile ID --profile-version VERSION (--all | --module MODULE) [--adoption FILE] [--baseline FILE] [--as-of DATE] [--check] --project DIR
lekalo architecture-profile diff --base-profile-report FILE --candidate-profile-report FILE
```

**Proposal:** v1 accepts supplied owner-specific evidence/config documents through a closed input manifest; later shortcuts into validate/CI must be explicit consumers of the same resolved policy. CLI selection conflicts with persisted assignments must refuse, not choose the looser policy. `--check` evaluates resolved gate obligations and cannot lower required evidence/confidence or substitute a weaker profile. Ordinary commands keep their own selection semantics until an explicitly versioned integration is delivered.

## Proposed profile format, inheritance and scoped opt-in

### Proposed four-profile contract

All settings in this table are **proposals**, not current CLI defaults. Named architecture profiles are independent of observed/contracted/generated ownership modes; choosing a name never changes who owns source or Model.

| Proposed profile | Parent and severity/evidence policy | Incremental/generation behavior |
| --- | --- | --- |
| `legacy-observed` | Explicit root. Preserve existing mandatory semantic/security/reference checks for any loaded canonical inputs. Optional native/architecture checks off or info/advisory, required evidence limited to what is deliberately assessed; partial/unsupported remains visible. | Start with explicit observed bindings and raw inventory; no compulsory full rewrite, no inferred canonical promotion. Optional adoption ledger records qualified debt separately from coverage gaps. |
| `contracted-standard` | Extends pinned legacy root, enables applicable contract/ID/binding/scenario/error checks as warning or existing producer severity; requires current declaration/conformance evidence in opted-in canonical modules. | Maintained handler ownership stays contracted. A module can graduate while other modules remain observed; stronger cross-boundary obligations are reported. |
| `ai-strict` | Extends pinned contracted-standard. Requires published complete evidence for selected measurable core rules and declared target rules; reviewed context/radius thresholds and immutable baseline refs. Warning finding may deny via explicit gate; do not promote producer warnings to invented errors. | Partial required target evidence denies with a gap explanation. Style preferences remain advisory. Adoption is an explicitly named temporary state, never indistinguishable from full strict acceptance. |
| `managed-generated` | Extends pinned ai-strict and adds required current ownership/input/generator/determinism/scenario receipts for artifacts declared generated. | Maintained paths remain outside generation authority. Unsupported generator recipes refuse the requested managed guarantee; profile does not invoke generation or clean. |

**Proposal:** service refs compile into selections accepted by existing decoders; architecture names do not appear inside today's off/advisory/ci enum. Preserve registered default-error severity exactly and keep mandatory checks enabled. For optional warnings, allow existing warning-to-info mechanics only with explicit declared change/provenance; restoring inherited info to registry warning strengthens policy, without a warning-to-error override. Numeric and evidence obligations are enforced by policy denial, keeping factual diagnostic severity separate from gate outcome.

### Proposed inheritance, weakening and diff

**Proposal:** single parent, exact ID/version/source/resolved digest, maximum eight links; reject cycles, missing parents, duplicate IDs/versions/rule changes, unknown members, foreign catalog ownership and stale digests. Resolve root to leaf in unsigned UTF-8 order for sets; inherited rule absence never implicitly disables it. Every resolved member carries declaring profile/version and whether inherited or changed. Built-ins remain immutable versioned artifacts; changing one requires a new version.

**Proposal partial order:** disabled < enabled, info < warning < error for selectable optional diagnostics; no error override at all for mandatory producer errors. For evidence: optional < required, partial < complete, confidence/claim/currency requirements can only strengthen without an explicit exception. Lower maxima or lower regression allowances strengthen numeric policy; reducing required-evidence sets, disabling gates, raising maxima, lowering confidence, removing a target, adding debt allowance or switching recipe can weaken/invalidate comparability. Different recipes are incomparable, never automatically "stronger". The resolver audits referenced service configurations after module merge; checking only the architecture rule list would miss coupling threshold relaxation or lint gate removal.

**Proposal weakening record:** exact scope/rule/member, parent old value/digest, proposed new value, owner, nonblank rationale, review ref and optional expiry. Mandatory semantic/security/reference errors and their enablement cannot be weakened. Other weakening must be explicitly declared and emits a visible policy-change; a child carrying an exception cannot claim unchanged built-in `ai-strict` acceptance. Module assignments only strengthen parent selections in v1; a temporary exception uses the separate adoption/exception identity. This follows the target-profile acknowledgment principle without inheriting its capability grammar.

**Proposal diff rows:** keyed by scope/rule/member, `{before, after, changeKind, strength, sourceProfiles, rationaleRef, evidenceRefs}`. Change kinds include add/remove/enable/severity/evidence/threshold/target/recipe/baseline/adoption/ownership requirement; strength is strengthened/weakened/incomparable/unchanged. Compare both source documents and effective snapshots: parent/rationale/acknowledgment changes are visible even when effective values match. No hidden defaults, glob precedence, last-wins merge or CLI severity overrides. A lower active count caused by disabled rules/waivers/coverage loss is a policy change, not measured readability improvement.

### Proposed scope grammar

**Proposal:** exact closed selector union `{kind:"project", id:<exact project identity>}` or `{kind:"module", id:<exact semantic module ID>}`. Assignments are `{scope, profileRef}` with at most one project assignment and one per module; unknown identities and duplicates refuse. No wildcard, path glob, folder, symbol subset or recursive module glob in v1. Runtime module IDs resolve against accepted IR; observed-only module assessment requires an explicit index-to-module identity and records unavailable canonical coverage, not fabricated empty Model.

**Proposal precedence:** project default then exact module strengthening; unassigned scopes remain unchanged/advisory. Catalog declares subject ownership. A local operation finding uses its owner's assignment; a cross-module SCC/shared-state/closure finding uses project obligation plus the strongest applicable participating-module requirements. Project selection cannot be narrowed by CLI `--module` to drop shared dependencies or participants. Read/dependency closure may cross opt-in boundaries; include witness/coverage from other modules without silently migrating their ownership or enabling every rule there. Ambiguous scope/subject ownership refuses or remains an explicit gap. Profiles are policy inputs, never new Model fields.

Illustrative **proposed assignment document fragment**:

```json
{
  "schemaVersion": "lekalo/architecture-profile/v<V>",
  "identity": "dev.lekalo.architecture-profile@<V>",
  "assignments": [
    { "scope": { "kind": "project", "id": "dev.example.planner" }, "profileRef": { "id": "legacy-observed", "version": "<V>", "digest": "sha256:<digest>" } },
    { "scope": { "kind": "module", "id": "planner" }, "profileRef": { "id": "ai-strict", "version": "<V>", "digest": "sha256:<digest>" } }
  ]
}
```

This is only the assignment fragment; a complete proposed document also carries catalog refs and profile declarations. Project/target IDs are synthetic illustrations that must resolve, not wildcard conventions imported from another profile family.

## Proposed baseline/adoption mode mechanics

**Proposal:** use existing typed #75/#76/#77 reports as immutable measurement baselines through exact refs. Add a distinct architecture adoption ledger for legacy violations, because a numeric coupling baseline and an AI-lint waiver do not mean "all fifteen requirements adopted". Ledger pins schema/catalog/profile source and effective digests, project/scope/target recipe, reviewed baseline reports/source revision, explicit as-of date and an exact set of debt entries. Never write or accept a baseline as a side effect of assessment.

**Proposal debt entry:** `{id, ruleId, ruleRevision, subject, targetRef, findingRef, conditionDigest, owner, reason, reviewRef, expiresOn, exitCriterion}`. Exact known finding/condition matching, no globs/all-rules/global-ignore. An expiry requires explicit `--as-of`; equality is active through that date. Owner/reason/review/exit criterion are required and bounded. Keep original finding/metrics, active debt, resolved debt and expired/orphan/changed-condition audit rows. Unqualified inferred findings may remain advice, but unknown/unsupported required evidence, malformed sources, ambiguous resolver failures or mandatory errors cannot become accepted debt.

**Proposal adoption states:** `inventory` (coverage/raw measures), `adopting` (qualified pinned debt with no unexplained new qualifying violations), `enforced` (selected required coverage current/complete, all gate obligations met, no debt for those obligations). A valid advisory report may be useful in inventory; adopting does not claim full ai-strict acceptance. Strict final assessment requires enforced state for its required rules; a deliberately selected adoption check can accept pinned debt and must state adopting. This gives legacy consumers a working migration gate without falsely advertising a fully conformant profile.

**Proposal workflow:** record current explicit observed inventory; choose contracted-standard for one exact module and perform the existing explicit promotion/declaration/attachment actions under their own commands; collect current native evidence; review exact debt and metric baselines; gate new qualified regressions; discharge debt with independently verified evidence; then opt that module into full ai-strict. Moving source does not automatically discharge debt or promote a binding. New unrelated debt, worsening a measured debt condition, lost coverage, stale toolchain/source pins or weakened service config denies the adoption check until an explicitly reviewed ledger successor records the change.

**Proposal comparison:** compare raw structural vectors only under compatible scope/subject mapping/recipe/target/evidence coverage. Changes to architecture selection, waiver/ledger, detector coverage, thresholds or baseline refs are separate policy rows; incompatible numeric series stay unknown/incomparable. Accepted semantic rename history may match subjects; ambiguous identity mapping cannot. Baseline pins stay byte-specific even if display text changes. No baseline subtraction from raw counts, no zero by missing report, no automatic Git checkout/history database or paid provider execution.

## Proposed determinism, lock/diff and measurable evaluation

### Proposed deterministic custody

**Proposal:** canonical UTF-8 JSON, LF, sorted set-like catalog/profile/rule/scope/evidence IDs; preserve ordered witness/activation chains. ## Risks and proposed delivery stages

- **Meaning versus policy:** severity/evidence is not Model semantics. Lock/diff work must show policy changes without adding Model fields, fake native edges, new impact seeds or altered operation/error meanings.
- **Hidden weakening:** retaining a warning while disabling its gate, enlarging a closure threshold, narrowing target scope or accepting a new baseline can relax policy. Resolve and compare every effective service selection, not only catalog severity.
- **Evidence coverage:** current PHP token collection is partial; Mago finding-only coverage cannot prove clean execution; finality is not readonly. Required gaps stay visible, even during adoption.
- **Adoption laundering:** a baseline cannot excuse an unknown proof or mandatory error, and an adopting module cannot claim full strict compliance. Ledger additions/expiry/config changes stay audited separately from structural improvement.
- **Cross-module scope:** traversal must retain dependency witnesses outside selected modules. A local assignment must neither hide shared state nor unexpectedly migrate another module's ownership.
- **Style and measurement:** a low token/depth/radius number can remove necessary facts or abstractions. Qualified completeness and preserved behavioral gates are prerequisites; R4/R14 broad preference remains advice.
- **Shared successors:** registry/profile/schema/lock/diff/protocol/adapter pins and suite ownership are integration seams. Re-inspect the implementing base, preserve the union, choose product-version successors and run all existing producer gates on the actual merged candidate.
- **Empirical claims:** structural indicators are not AI outcomes. Agent/model/version/context changes and task leakage can dominate A/B results; use frozen independent trial evidence and report uncertainty/negative outcomes.

**Proposal stages:** (1) freeze rule catalog/ownership/applicability and four-profile semantics; (2) deliver closed resolution/scopes/explanations with existing measurable producer facts and explicit gaps; (3) add qualified adapter clean coverage and required native signals; (4) integrate immutable adoption/baselines and lock/diff/evidence successors; (5) complete synthetic/real-tool/union CI acceptance; (6) execute separately authorized reproducible A/B evaluation.
