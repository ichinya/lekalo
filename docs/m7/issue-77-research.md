## Proposed command/report schema

### Command and ownership

Proposed CLI grammar, reusing the existing global `--json` and project selector:

```sh
lekalo --json coupling --symbol planner.task
lekalo --json coupling --symbol planner.task --field state
lekalo --json coupling --module planner --coupling-profile project-arch --profiles config/coupling-profiles.json
lekalo --json coupling --all --coupling-profile arch-strict --profiles config/coupling-profiles.json --baseline reports/base.coupling.json
lekalo --json coupling --changed-input reports/change-input.json --evidence reports/coupling-evidence.json
```

Exactly one selector: symbol, module, all, or a typed changed-input file. `--field` is legal only with a symbol that has that declared field. A missing/ambiguous id is invalid; no first-match resolution or string-prefix field parsing. Module/all selectors produce per-symbol and supported per-field rows plus deduplicated module/project summaries; a module import node alone is not a symbol report. Existing `ChangedInputSet` is an in-memory handoff, not a published input-file schema. Proposed `--changed-input` therefore has its own closed coupling change-input schema/decoder, constructing existing `ChangedInputSet::from_entries` and member seeds; direct in-process callers reuse the typed set. There is no second Git parser. No automatic Git checkout, scan, generation, provider call, native-test run, baseline update, cache write or report persistence. Filesystem joins occur in a bounded CLI adapter using `project_fs`; core receives immutable typed inputs.

Without a named coupling profile, report structural facts under a pinned built-in measurement recipe, with no numeric risk threshold and advisory assessment. A named profile supplies a recipe, project/module limits, centrality declarations and an advisory/strict gate mode. An explicit baseline is required for strict regression policy; missing or incomparable required evidence denies rather than silently skipping. This is the proposed **coupling strict profile**, not an overload of validation `--strict` or `ImpactProfile::Strict`. Users can redirect stdout; no new conventional `.lekalo/**` home is assumed.

### Report and evidence shape

Proposed top-level success attachment `coupling` has `schemaVersion`, `identity`, `metricVersion`, `scope`, `recipe`, `profile`, `provenance`, `coverage`, `subjects`, `summary`, `witnesses`, `findings`, `suggestions` and `planning`. An optional separately versioned `couplingComparison` carries baseline deltas; denial retains the report plus registry diagnostics in the terminal envelope. Proposed identity: `dev.lekalo.coupling-report@<V>`; discriminator `lekalo/coupling-report/v<V>`; metric recipe version `coupling-metrics/1`. Do not insert these members into existing graph/impact/context report schemas.

Each proposed subject identity is a kind-qualified owner id plus an optional typed member key, e.g. entity `planner.task`, member `field.state`. Keep fields in the coupling projection rather than extending the canonical graph kind registry. Proposed `impact` partitions contain `publicContracts`, `internalSymbols`, `supportingSymbols`, and `unclassifiedSymbols`, each with stable ids, count state and witness refs. Root contracts participate in changed-contract count; direct neighbor counts exclude roots and self-links. Modules/project summaries count unions, never the sum of overlapping per-root closures. Publish both per-kind contract counts and their exact unique union.

Proposed numeric state wrappers are `known|unknown|withheld|unsupported`; only known carries `value`. An incomplete walk reports its proven lower bound separately, never an exact count. Field overapproximation has a separate `possible` set and `basis: owner-conservative`; it must not masquerade as a lower bound. Exact declared coverage and unknown observed coverage are independent. `coverage` explains selected/unselected capabilities, stale inputs and truncated witnesses; missing evidence is not zero.

Proposed witness entries carry root/subject identities, traversal direction, ordered canonical edge keys (including relation/occurrence), reference roles, effect or attachment references, confidence meet and exact source attribution. Reverse discovery direction is explicit even though stored edges point from dependent to dependency. Structural metric bytes/digest exclude source paths/spans; an optional source-location view joins `Compilation::source_map` or current observed/artifact maps, with normalized project-relative paths and exact JSON pointers/spans. Default semantic witnesses remain useful without physical paths. No absolute paths, source bodies, environment, secrets or wall-clock timestamps are included. Diagnostic list limits do not cap the metric closure: retain complete evidence in the bounded report or mark it incomplete, with diagnostic refs into that report.

### Baseline, trend and semantic-diff boundary

Proposed baseline input is the exact prior coupling report payload, not an envelope, context-budget report or mutable waiver list. Decode it with closed typed structs, duplicate-key rejection, known-state/value coupling and independent arithmetic/set validation. Pin exact baseline file bytes and its semantic/evidence revision. A missing file/input is an error or required-baseline denial; malformed baseline is invalid, not merely incomparable. Unrecognized contract/recipe versions are unsupported-version.

Compare metrics only under identical measurement recipe/version, scope semantics, public-contract classification, required attachment versions and capability coverage. Revisions and consumed evidence digests should differ across revisions; validate each against its own revision instead of requiring equal revision digests. Separate `measurementDigest` from full profile/configuration digest: a threshold or gate-mode edit changes policy provenance but need not destroy otherwise valid trend. A relation/field/public-surface recipe edit does make affected rows incomparable. Neither two unknown values nor a lower bound is a comparable exact numeric pair.

Match stable symbol/member ids; accepted same-identity rename history can map owners, with explicit mapping evidence. New/deleted rows remain added/removed, not zero-based regressions. No implicit field rename heuristic. Emit signed absolute deltas, rational relative increases and per-metric comparability reasons. When baseline is zero, relative growth is unavailable with `zero-baseline`; evaluate the explicit absolute allowance, never infinity or fabricated zero percent. Counts must reconcile with sets, amplification components and SCC witnesses before gate evaluation.

Default trend output is advisory. A proposed strict profile can deny when a comparable required metric grows beyond its configured allowance, or when required baseline/completeness is missing. Exceeding either configured absolute or relative allowance fails; equality passes. Optional unavailable metrics do not block unrelated complete comparisons. Absolute limits can become strict only after an explicitly configured baseline readiness pin; collecting the first report never silently creates a hard gate. Baselines are reviewed inputs and never rewritten by lint or regenerated by normal CI. Suppression/centrality declarations retain raw metrics and deltas.

Current `diff::compare` equality and compatibility classes stay intact. A future opt-in comparison consumer may attach the proposed coupling comparison beside semantic-diff/QA output after an explicit schema successor, using both accepted compilations and the same coupling recipe. Until that consumer exists, callers run coupling/baseline comparison separately; the proposal does not claim current diff already embeds architecture metrics. File reformat/split cases produce equal semantic coupling even if location or provenance bytes change.

## Metric definitions with data sources

### Projection, closure and public/internal semantics

Proposed architectural graph A includes dependency-bearing semantic roles: typed field references, command input/effect references, query reads/returns, effect subjects/emissions and endpoint invocation. `requires` imports form their own module series; `derived_from`, scenario coverage, test verification and authorization applicability are supporting facts rather than fan-in/out architectural edges. Admitted current attachment contributions stay labeled by their owning contract/role. A role-qualified recipe prevents generic `references` edges from conflating type dependency and scenario coverage. Project/module container nodes do not become symbol neighbors.

Forward fan-out answers what a subject depends on; reverse closure R answers what may need review when it changes. Traverse internal intermediates before classifying endpoints. R includes roots and all admitted semantic dependents until the frontier is exhausted; public results cannot be clipped by a rendering depth or an internal-only display filter. Follow incoming policy/scenario coverage after dependency propagation as supporting context; do not feed those edges back into arbitrary dependency expansion. Effect/resource and transaction contributions have separate typed hops and witness kinds.

For the proposed core public-contract series, project-visible entities, named types, commands/queries, events and endpoints are contracts; omitted visibility follows the existing project default. Module-visible definitions are internal. Policies/effects/scenarios/target bindings are supporting semantic surfaces, not extra public contracts merely because visibility is project-wide. Target exports form a separate evidence-backed public series; they do not silently widen canonical public counts. Report unclassified observed exports explicitly. This is a versioned metric classification, intentionally narrower than impact's general public risk subjects, not a change to Model visibility or semantic validation.

Field propagation starts with explicit typed references/effects/query selections and whole-record consumers. Whole-record input/output or entity-wide effect is labeled as possible field sensitivity unless the member's participation is established by the owning contract. Unsupported attachment roles or unresolved bindings leave exact member influence unknown. An entity-owner fallback is useful as a conservative possible radius, but cannot supply a proven exact count or a strict threshold violation. Fan-in/out for fields counts only attributable references; whole-symbol fan metrics remain independently available.

## Determinism strategy

Proposed metric identity binds the semantic projection digest, Model/graph/effects/attachment contract identities, consumed evidence pins, selected role recipe and coverage, with a separate effective configuration digest. Layout/source attribution is a separate view. Canonical byte order comes from explicit kind/semantic-id/member/edge ordering, not hash-map iteration, platform paths, filesystem discovery order or timestamps. Sorting diagnostic/report keys uses the owning contract's canonical rules, not a universal reserialization of unrelated accepted contracts. Relative deltas use checked integer rational arithmetic.

Build adjacency, module projections, resource-writer indexes and SCCs once; traversal uses visited keys and canonical parent maps. Reuse components/memoized summaries where applicable; avoid all-path enumeration and unbounded per-field/per-symbol Cartesian closure. Proposed hard ceilings: no larger than graph/query ceilings; <=2,000 selected subject rows, <=1,000,000 cumulative edge visits across a request, <=50,000 proof nodes/250,000 proof edges per closure, <=256 edges per rendered witness and <=32 MiB serialized report. These are implementation proposals requiring boundary tests, not claimed current coupling constants. Exhaustion records incomplete metrics/frontiers; witness truncation never silently asserts an exact full path. Full metrics may remain known if only the separate location/rendering view is bounded. Use a proved lower bound only for predicates it actually establishes; a conservative possible set cannot prove a minimum radius.

## Profile format

Propose a closed `coupling-profile` document selecting one versioned measurement recipe plus project defaults, exact module-id overrides, explicit domain groups/replica obligations, centrality declarations and gate policy. Do not mix its members into current validation profiles. Unknown metrics/roles/module ids, duplicate/conflicting overrides, negative/noninteger counts, zero relative denominator and unsupported versions fail closed. No wildcard override precedence in v1. For cross-module/group findings, the subject owner selects numeric overrides; SCC/resource-wide strict limits come from project policy, so traversal order cannot choose the laxest participating module.

Illustrative **proposed configuration fragment** (universal defaults are intentionally absent):

```json
{
  "schemaVersion": "lekalo/coupling-profile/v<V>",
  "identity": "dev.lekalo.coupling-profile@<V>",
  "profileId": "project-arch",
  "profileRevision": "1",
  "measurement": { "recipe": "declared-architecture/1", "includeObserved": false },
  "project": {
    "limits": [{ "metric": "publicContractsAffected", "maximum": 12 }],
    "regressionLimits": [{ "metric": "publicContractsAffected", "absoluteIncrease": 2, "relativeIncrease": { "numerator": 1, "denominator": 5 } }]
  },
  "modules": [{ "module": "planner", "limits": [{ "metric": "fanOutModules", "maximum": 3 }] }],
  "domainGroups": [{ "id": "task-lifecycle", "modules": ["planner", "tasks"] }],
  "centralityDeclarations": [{ "subject": "entity:planner.task", "reason": "Shared task identity and lifecycle", "reviewRef": "architecture/task-lifecycle", "rules": ["coupling.shared-abstraction-radius"] }],
  "gate": { "mode": "advisory", "failOn": [] }
}
```

This fragment is a proposed shape illustration, not a loadable current profile; ids must resolve against the selected project. A full proposed document closes all nested objects and defines absent members explicitly. Module `limits` and `regressionLimits` replace only matching metric entries and inherit the rest. Count maxima use `value > maximum`; growth is candidate minus baseline and only positive increases can regress. Unconfigured metrics remain visible without a numeric verdict. Configured required metrics carry explicit exact-coverage requirements, so unsupported artifact tests are optional unless the project deliberately requires them.

For a proposed `arch-strict` profile, set `gate.mode` to strict, `failOn` to selected `baseline-regression`, `required-incomplete` and optionally `threshold-exceeded`, and add a required `gate.baselineReadyRef` with the reviewed baseline report's digest. Strict baseline mode refuses missing, changed-without-review or incomparable baselines. The pin is an explicit calibration record, not a statistical assertion; reports can track a longer sequence of reviewed comparable baselines without an automatic storage engine. A profile can be stricter for selected required metrics without making every optional evidence family mandatory. No implicit hard limit of 19 contracts or 7 modules comes from the issue example.

Centrality declarations are scoped, justified and review-linked. They annotate necessary domain concentration and may waive a named advisory risk finding when the configured scope matches; they do not subtract contracts/writers, alter graph paths or automatically waive baseline regression. Proposed optional expiry needs an explicit `--as-of YYYY-MM-DD` input, included in configuration provenance; do not consult the wall clock. Default to declarations without expiry in this version if no evaluation date is supplied. Domain groups and duplicate obligations are typed configuration, not ignored prose. #76's eventual suppression contract may later be referenced through an explicit adapter/successor; it is not required to merge #77 independently.

## Risks

- **Semantic completeness:** counting edge occurrences, module imports, impact's supplemental public section or a depth-limited capsule can under/overstate radius. Full reverse traversal across internal nodes and explicit field/attachment coverage are necessary for an exact verdict.
- **Public-contract definition:** project visibility is broader than a transport API. Emit kind-specific canonical contracts and separate observed exports; freeze the chosen classification in the recipe rather than silently changing it with a profile threshold.
- **Field precision:** entity-wide operations, whole-record contracts and missing query/effect contributions often support only possible sensitivity. Conservative potential radius is useful advice, not evidence for a hard minimum count or exact strict regression.
- **Centrality and policy gaming:** shared identity/state can be necessary. Preserve raw vectors, domain groups and protections; scopes/waivers must not make growth disappear. Threshold edits need separate provenance and review even when metric trends remain comparable.
- **Cycles:** projected module cycles do not necessarily imply a symbol-level cycle. Import/requirement cycles already invalidate construction. Different witnesses and diagnostic ownership prevent these cases from collapsing into one false architecture error.
- **Artifacts and targets:** fresh ownership/trace/input refs are prerequisites for exact amplification. Broad module bindings, scenario coverage or stale manifests are not replacement evidence. A code generator's potential outputs are not automatically artifacts requiring review.
- **Inference overlap:** #76/adapters discover ambiguity and hidden behavior. Inferred detected writes stay confidence-labeled; #77 must neither resolve ambiguity nor claim zero risk because a selected observation is absent.
- **Scalability:** all-subject/member closure can become quadratic; global work/output caps, indexes and SCC reuse are required. Incomplete or truncated evidence must remain visible, and a denied strict run must retain its report.
- **Version/merge drift:** own modules/codes/gates reduce overlap, but registry/profile/suite/dispatch/CI pins are shared integration work. Re-evaluate after either branch lands; preserve union coverage and re-run both families on the actual merged revision.
- **Custody and privacy:** reports are local read-only analysis, not accepted public exports or scheduler commands. Location joins require existing classified reads; no new storage/export authority, source upload, HLV writes or baseline replacement is authorized.
- **AI-quality interpretation:** coupling vectors identify review/context costs and risk evidence. They do not prove a refactor improves understanding, parallel safety or performance; any such claim needs separately measured behavior and preservation evidence.

Proposed delivery stages: close own schemas/metric recipe/diagnostic allocations and fixture expectations; implement indexed projection/public/internal/member coverage; add cycles/shared-state/trace amplification; add immutable baseline/profile denial; finish exact advisory suggestions and planning consumer tests; integrate union registry/suite/CI with #76. All ten checks and seven acceptance rows remain required; a first fan-count report alone is not completion of #77.
