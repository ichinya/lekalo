That earlier research document is a design reference, not current implementation evidence.

**Decision (proposal):** a separate, optional, read-only `lekalo ai-lint` command and pure core analysis service. Core checks accepted Model/IR/graph, candidate identities, declared/detected effect differences, transition coverage and evidence joins. Adapters recognize language/framework mechanisms and supply bounded typed evidence; core never recognizes PHP or TypeScript syntax. Preserve mandatory resolution failures and existing validation defaults. Findings keep evidence, scope, confidence, explicit alternatives and suppression disposition; revision comparison measures a vector of structural indicators rather than claiming measured AI understanding.

**Proposal marking convention:** every section titled “Proposed”, every cell marked **Proposal**, and every example explicitly introduced as a proposed shape describes future work. All paths, APIs, members, identities, flags and diagnostic codes in those proposal scopes are proposals, including their repeated references. `<V>` is the implementation commit's product version, selected under `scripts/check-contract-versions.mjs`; it is not an allocated version in this research. No implementation, schema amendment, adapter rebuild, fixture addition or gate wiring is delivered here.

## Proposed command/report schema

### Proposed command and ownership

Every flag/API/path introduced in this subsection is a **proposal**. Existing global `--json` and `--project` conventions are reused.

```sh
# Proposed grammar; example input paths are caller-owned toolchain files.
lekalo ai-lint --all --lint-profile advisory --config config/ai-lint.json --json
lekalo ai-lint --symbol planner.focus_task --lint-profile advisory --config config/ai-lint.json --evidence reports/php.lint-evidence.json --spans --json
lekalo ai-lint --module planner --lint-profile ci --config config/ai-lint.json --waivers config/ai-lint-waivers.json --as-of 2026-10-03 --check --json
lekalo ai-lint --all --lint-profile advisory --config config/ai-lint.json --scan-target php --json
lekalo ai-lint --all --lint-profile ci --config config/ai-lint.json --baseline reports/base.ai-lint.json --check --json
```

Require exactly one selection: `--symbol`, `--module`, `--all`. No automatic lint invocation from ordinary `validate`, `observe update`, inspect, generation or native tests in v1. Supplied evidence is the default target mode; a Model-only run can omit it and reports target rule coverage as unsupported/unknown. `--scan-target` explicitly requests a read-only installed adapter collector; reject combining collection and supplied evidence for the same target. No package install, Composer/Artisan boot, app import, hook invocation, database/network access, native execution, provider request, binding confirmation, source edit or history write is part of lint. Necessary bounded transport staging is temporary infrastructure, not a new persisted project artifact.

**Proposed input pipeline:** load/normalize/compile, run the existing mandatory semantic/reference validation, validate each supplied attachment against its Model/IR pins, then admit observed/target evidence and build the accepted graph/effects views. Pass terminal failures through before lint. Observed-only rows do not require promotion into Model definitions; where a canonical scope is absent, canonical-only rules explicitly lack applicable coverage while observed binding/target rules can still assess their typed inputs. Never turn arbitrary native scan edges into accepted #13 edges.

`--check` evaluates the selected profile's mandatory gate; ordinary invocation is advisory even under the same rule selection, and the report identifies the invocation mode. CI must pass the checked-in config/profile and `--check` explicitly. Missing required pins/evidence/baseline cannot turn a mandatory invocation into an advisory pass. `--baseline` reads immutable prior report bytes and never replaces them.

### Proposed evidence and confidence contract

**Proposed evidence shape:** `{schemaVersion, identity, producer, sourceRevision, modelRef, irRef, observedRef, targetRef, inputManifestDigest, coverage, records, locations, limitations}`. Every member and variant listed here is proposed. `producer` binds adapter ID/version/artifact digest, tool/compiler/framework identities and detector recipe/version. References use exact version plus digest; unavailable references use explicit four-state wrappers, never fabricated hashes/null. `targetRef` includes resolved profile/capability digest. `inputManifestDigest` covers every read source/config/binding/declaration file; evidence carries per-file fingerprints so the admitting CLI can verify current bytes with confined reads. Revision labels alone are insufficient.

**Proposed coverage rows:** `{ruleId, targetId, scope, eligibleSubjects, examinedSubjects, state, limitations}` with state `complete/partial/unknown/unsupported/withheld`; eligible and examined counts use `known/unknown/withheld/unsupported` value wrappers. A zero finding count means “clean within this complete recipe/scope”, only when its coverage is complete. `records=[]` alone never proves absence. Unsupported target/framework versions and dynamic/external boundaries retain explicit gaps; required coverage policy can deny them.

**Proposed record union:** structural binding candidates, dispatch sites, convention paths, effect sites, owner/trace joins and target defaults. Common proposed members: `{recordId, kind, subjects, operationRef, nativeRef, locations, origin, confidence, currency, condition, evidenceRefs}`. Kind-specific proposed members include `candidates` and their resolution conditions; `callKind`/`calleeCandidates`/`bindingEvidence`; `mechanism`/`activationChain`/`effect`/`guards`; `configEvidence`; `ownerEvidence`/`traceEvidence`; and `defaultKey`/`value`/`effectiveScope`. Closed unions prohibit irrelevant members. Native external/unresolved targets are explicit alternatives; they do not enter the accepted #13 graph as unresolved edges.

**Proposed activation chain:** command binding -> call/emit/model mutation -> registered observer/listener/hook -> effect site, with evidence IDs and guards on every link. A hook class or event-name match alone proves no activation. Per-effect records name kind/action/resource/optional exact field, and a chain may claim only a potential effect until its activation and runtime conditions are independently established. A digest cannot authenticate an adapter assertion; admitted origin and proof qualification remain visible.

**Proposed location:** logical confined project-relative POSIX path, source digest, 0-based half-open UTF-8 byte range and 1-based line/column range. Validate range against the pinned source bytes; convert TypeScript UTF-16 offsets explicitly rather than treating them as UTF-8 bytes. Model locations come from occurrence-safe source maps; target locations come from adapter evidence. Definition, registration, invocation and write spans are different related locations. Existing observed path/line is insufficient for an invented exact range: missing range is a coverage limitation.

**Proposed claim kinds:** `structural`, `possible-behavior`, `verified-behavior`, separate from proposed finding confidence `exact/high/medium/low/unknown`. “Exact” for a static declaration or binding is not proof the runtime executes a write. A verified-behavior claim requires qualified current execution evidence from its existing owner, covering this operation, target, revision, guards and effect. #76 does not introduce a runtime proof executor. Inferred behavior remains possible-behavior even if every syntax site is precisely located.

### Proposed report shape and projection

**Proposed report shape** (every member is proposed): `{schemaVersion, identity, scope, mode, pins, asOf, coverage, findings, summary, metrics, waiverAudit, comparison}`. ### Proposed framework-specific evidence boundary

Laravel documentation was fetched through Context7 `/laravel/docs` and its `13.x` version, matching the existing planner fixture's pinned `laravel/framework: 13.33.0` (`tests/fixtures/php-laravel/planner/composer.json`). Observers require registration through the documented attribute or `observe` mechanism; Eloquent mass update/delete paths bypass the per-model events described there; after-commit observers have transaction-dependent scheduling. These facts justify registration/activation/guard negatives, not a claim that every observer method executes. [Laravel 13 Eloquent documentation](https://github.com/laravel/docs/blob/13.x/eloquent.md).

Laravel can automatically resolve concrete-class dependencies; interfaces require explicit binding. Consequently the proposed locator rule tests missing effective binding evidence and ambiguity, not every use of the container or lack of a redundant concrete-class registration. Parsing a plausible class name is insufficient to resolve an interface/service string. [Laravel 13 container documentation](https://github.com/laravel/docs/blob/13.x/container.md), [Laravel 13 helper documentation](https://github.com/laravel/docs/blob/13.x/helpers.md).

Node 24 EventEmitter documentation was fetched through Context7 `/websites/nodejs_latest-v24_x_api`, matching the build-test Node major. `emit` calls registered listeners synchronously and discards their return values; listener registration/removal and `newListener` can change the applicable set/order. **Proposal:** the Node collector records receiver identity, event key, registration site, callback and effect chain, retaining runtime guards and limitations. Static registration plus a possible emit supports possible behavior; it is not observed execution. Unknown emitter implementations do not inherit this recipe. [Node 24 events documentation](https://nodejs.org/docs/latest-v24.x/api/events.html).

These are documented API semantics. Choosing detector coverage, confidence ceilings and alternatives is a design inference in this research. Collection must pin the actually selected runtime/framework version and support state; neither current web documentation nor a similarly named local method establishes that a target uses these APIs.

**Proposed state-writer grouping definition:** for each exact resource/field, deduplicate writer sites by bound command. A command is transition-covered only when a current validated transition names that command, the same state-space resource/field and an assignment of that field. Count uncovered commands as independent groups unless an explicit, justified config group enumerates their exact IDs and the common owner; the proposed config member `relatedWriterGroups` carries those bounded memberships/owner/reason. File/module proximity never groups writers. Unknown field identity, command binding or declaration coverage makes the group count unknown. With complete selected declarations, an empty transition set proves only “no transitions declared in these supplied inputs”, not absence of runtime state control.

## Proposed determinism strategy

**Proposal:** pin rule recipe/versions, accepted contract identities, source input manifest, target/profile/toolchain, evidence admission algorithm, effective config, waiver digest and explicit evaluation date. Pure core analysis uses canonical identity order; read/collection order cannot change results. No ambient clock, locale, path casing heuristic, host path, random ID or provider choice participates in findings.

**Proposed finding identity:** SHA-256 of a versioned canonical tuple `(ruleId, subject identity, target/context identity, mechanism, resource/field or binding key, stable native identities, semantic witness keys)`. Exclude revision labels, span offsets and display text so an unchanged finding survives source movement. Keep a separate proposed `conditionDigest` over the relevant evidence/config/source fingerprints for suppression applicability. A changed condition revokes the waiver even if the finding identity is stable. Preserve original evidence digests/revisions separately for audit; no digest claims anonymization or authenticity.

**Proposal:** normalize set-like candidates/subjects/evidence refs/waivers by unsigned UTF-8 identity bytes, preserving behavioral call/activation order. Deduplicate only identical machine evidence and equivalent rule/subject/effect witnesses; do not collapse contradictory producers. Choose a shortest witness with canonical tie-breaking while measuring maximum SCC-condensed depth with a deterministic DAG pass. Depth counts inter-component edges; membership/recursive structure is separately visible. Semantic recipe selects existing relation keys (`references`, `accepts`, `returns`, `reads`, `emits`, `exposes`) explicitly, and excludes module `requires` fan-out, inverse authorization/test edges and source folders unless a separate declared metric recipe selects them. Native-call recipe stays separate.

**Proposed hard caps:** at most 10,000 selected subjects, 50,000 analyzed nodes, 250,000 analyzed edges, 10,000 evidence/finding rows per document, 32 witness steps/related locations per finding, 8 MiB per evidence/report payload, and 10,000,000 deterministic work units per invocation; caller limits may tighten but not increase them. Enforce checked integer arithmetic and bounded source reads under the existing filesystem/transport caps. Both schemas and production decoders enforce the same caps and reject duplicate keys, unknown members, null state substitutions, invalid spans and extra bytes.

Graph/input construction failures pass through their existing terminal diagnostics. A lint algorithm's own exhausted work/selection bound yields explicit partial rule coverage, unknown affected metrics and a coverage diagnostic; a short demonstrated over-limit witness may remain a lower-bound finding, but no complete maximum or clean verdict is claimed. Do not silently downgrade an existing `graph.traversal-limit` error to a valid diagnostic: operate on accepted graph indexes with the lint service's explicit bounded-result contract. Within the existing 256-diagnostic projection bound, reserve space for policy/coverage summaries and expose projection truncation; the richer report retains all admitted bounded findings. Reaching the report bound must make incompleteness visible, never silently lose findings.

## Risks

- **Resolution semantics:** optional lint must not weaken mandatory loader/inspect/binding/lock/scenario refusal or silently change user-owned mappings. Ranked candidates, multiple targets and incompatible contexts need distinct treatment.
- **Evidence overclaim:** syntax/type resolution, exact spans, current digests and a successful adapter process do not prove a runtime effect. Unknown activation/coverage must remain visible; proof qualification is an independent contract obligation.
- **Field/transition precision:** entity-level CRUD does not identify a status field; incomplete declaration/transition inputs cannot justify “without transitions”. Directory separation does not identify unrelated business operations.
- **Unsupported PHP surface:** present PHP scan cannot carry full native hooks. New collector/protocol support and real fixture-producing gates are necessary dependencies, not claims fulfilled by research.
- **Profile and waiver abuse:** a severity promotion is forbidden by existing profiles; use explicit policy denial. Waivers must not alter binding/evidence truth, apply across changing conditions, reduce raw counts or bypass mandatory security/authority.
- **Depth interpretation/scale:** semantic references are a proxy; native calls require independent adapter facts. Cycle condensation, bounded work and canonical witnesses avoid infinite/exponential traversal, while incomplete depth never becomes a smaller proven maximum.
- **Version and consumer skew:** diagnostic wire, registry, target protocol, Model/IR, profile and report versions are different. Current pins must be inspected rather than copied from older reports; successor decoder/CLI/adapter/schema/status tests must agree.
- **Privacy and custody:** source spans, owner reasons and native names may be private. Default projection withholds paths/source; explicit local spans remain confined and policy-controlled. No public artifact/home, telemetry, persisted trace ownership or history/export authority is created.
- **False positives and trend distortion:** framework magic can be intentional. Negative fixtures, precise scopes, declared alternatives and audited waivers matter; disabled rules, lost coverage or new waivers cannot be presented as an AI-readability improvement.

**Proposed implementation sequence:** close report/config/evidence/waiver/diagnostic identities and protocol successor; build admission/projection and pure Model/graph rules; add actual PHP/Node evidence collectors with negative controls; wire production CLI policy/waivers/comparison; integrate producing fixtures and CI gates. Completion requires all seven acceptance criteria and all eleven check boundaries, not only warnings on a synthetic core graph.
