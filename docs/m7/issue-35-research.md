## Proposed command/report schema

### Adapter placement and command decisions

**Proposal:** do not add `lekalo hlv`, a core HLV runner or a new `trace export` grammar. Consume existing `provider describe --json`, then prescribed read-only operations from `docs/provider-contract.md`: validation with `--no-cache`, drift via `generate --check`, verify, readiness, and `trace export PATH --json`. Never execute command strings from discovery. Requested targets/changed modules/trace paths remain explicit; preserve their evaluated scope.

**Proposal:** add Extension-only `scripts/lekalo-hlv-bridge.mjs`, APIs `validateBridgeMapping`, `resolveHlvInventory`, `composeBridgeTrace`, `assessBridgeEvidence`, and `scripts/lekalo-hlv-bridge.test.mjs`. Update the existing Extension `lekalo-provider.mjs` to negotiate the landed Lekalo manifest; update `aifhub-providers.mjs` to run the bridge after retaining Lekalo/native results and qualified HLV results. These are future changes in another repository, not authorized mutations in this worktree.

**Proposal:** keep composition pure over validated documents. It accepts the exact neutral manifest, explicit mapping, native HLV inventories and independent provider/native receipts; it emits a neutral trace using only current node/relation/gap members plus a bridge assessment. Paths/processes/revision capture stay in the Extension host. No HLV source dependency enters `crates/lekalo-core/Cargo.toml` or core IR. If a reusable strict chain validator is later moved into core, it must operate only on neutral typed inputs, with a separately reviewed API proposal.

HLV `v1.0.0` is a structural format target, not permission to run its mutating check against the original project. **Proposal decision:** the first real bridge E2E uses a bounded isolated validation snapshot, with a reviewed input-copy recipe and explicit gate-execution authorization. HLV receives `['--root', snapshotRepoRoot, 'check', '--json']`; its own results and gate writes remain in disposable snapshot custody. Exact original revision/input fingerprints bind the snapshot before execution. Afterward, recheck original inputs, retain result fingerprints, and record which execution mode ran. If snapshotting the configured gate/environment faithfully is unsupported, return unsupported; never fall back to the live source tree. This research creates no snapshot and executes no gate.

**Proposal production prerequisite:** qualify snapshot mode per tool/target, or qualify an upstream read-only result protocol before enabling live-project checks. Do not silently rewrite `milestones.yaml`, change strictness to relaxed to suppress execution, insert HLV markers, initialize `.hlv/`, create test specs, or alter contracts/gates/requirements. HLV's own internal side effects must be disclosed in the reviewed execution recipe. A simple outer process timeout is insufficient proof of isolation.

### Neutral manifest decision

Reuse the current shape, identity and digest algorithm. A conceptual complete chain is represented by these **existing** directed relations:

```text
gate --evidences--> native_test --verifies--> scenario --covers--> symbol --implements--> requirement
                                                                symbol --binds--> artifact
```

**Proposal semantic rule:** a bridge-complete row must prove the requirement/symbol pair, the same symbol's selected binding artifact, the selected scenario's coverage of that symbol, the explicit scenario-to-HLV-test mapping, the specific test-to-HLV-gate relation, and compatible fresh evidence for each selected role. A direct gate -> symbol or scenario -> requirement shortcut cannot satisfy the full #35 chain. Check every in-scope requirement, binding and scenario selected by the mapping policy, not just whether at least one gate reaches a requirement. Requirements may have many symbols; scenarios/tests/gates may be many-to-many. Preserve each occurrence and all failed/gap rows.

HLV contract IDs may be kept in existing symbol `externalRefs`, and HLV test/gate IDs in native_test/gate refs. **Proposal:** an explicit mapping row carries the richer contract/test-spec pairing; an external ID alone never asserts that a Lekalo symbol is semantically identical to an HLV contract. Keep one neutral requirement node per selected canonical requirement identity. Existing HLV requirement ID is an alias to that identity only when explicit owner-bound mapping proves it; a conflicting statement or alias is a reportable conflict.

**Proposal:** separate two facts: a declared structural mapping can be confirmed against its cited revision/digest; an executed gate can still fail. The neutral trace has no pass/fail member. Attach the terminal check/native verdict in the bridge evidence assessment and never infer passing validation from `completeness: full` or `status: confirmed` on a relation.

### Mapping and assessment contracts

## Determinism strategy

1. Reuse neutral canonical order and relation tuple domain. No universal JSON sorter: trace uses fixed contract field order/no LF; provider discovery hashes canonical sorted manifest without its self-digest; Extension HLV trace summary currently hashes JSON.stringify payload bytes with a bare hex digest. Keep each digest's algorithm/domain explicit and do not reinterpret one as another.
2. **Proposal:** sort mapping/chain/gap/conflict outputs by documented UTF-8 byte tuples of requirement, symbol, artifact, scenario, HLV contract/test/gate and occurrence. Preserve ordered scenario steps; qualified original IDs remain byte-exact. Host locale and directory enumeration order cannot select a mapping.
3. **Proposal:** derive opaque neutral node identities from a qualified identity tuple when foreign IDs violate neutral grammar or collide. Store original IDs in externalRefs and the local assessment. An ID hash is a lookup key, not anonymization or evidence of semantic equality. Every occurrence relation uses `Relation::canonical_id` or an independent compatible implementation.
4. **Proposal:** bind original Git commit plus the worktree-input digest, Model/IR/artifact/lock digests, trace/mapping/native HLV input digests, target scope, effective provider/bridge policy, HLV strictness, execution mode/recipe and every protocol/tool identity. Branch name, file path, timestamp or installed-tool version alone is insufficient. Preserve both source-input and result digests for snapshot execution.
5. **Proposal:** enforce the smaller of producer and consumer bounds before expansion. Current Extension trace limits 2,000 requirements/mappings, 2,000 diagnostics and max configured 4 MiB process output, while Lekalo export can reach 32 MiB. Refuse unsupported oversized inputs with explicit reason; no silent slicing or raising provider limits. Bound rows, inventory files/bytes, duplicate keys, nested objects and join work. Ordinary source-copy runtime limits belong to the proposed snapshot recipe.
6. **Proposal:** deterministic structural payload excludes wall clock/absolute snapshot path/raw streams. Operation timestamps and actual execution metadata live in the outer evidence envelope. An actual runtime result is an observation and need not byte-match a previous run; never force fake determinism by erasing a failure. Same validated structural inputs/mapping/policy must yield the same graph and coverage result.
7. **Proposal:** make persistence idempotent and failure-isolated. Validate every new document before atomic write. Never delete another provider's files, native receipts or scenario records on HLV failure. Preserve failed current-attempt evidence independently from last-success evidence; done cannot choose an older success after a newer fail at the same pins.

## Risks

- **External adapter lag:** the published Lekalo handshake and Extension's fail-closed 0.1.10 stub do not interoperate today. Closing #34/#136 does not establish real three-provider E2E acceptance. Coordinated Extension protocol/evidence successors are required.
- **Check side effects and layout mismatch:** pinned HLV can execute commands and save gate results to repository-root milestones.yaml. Live checks could mutate inputs, trigger providerRevision invalidation or produce incomplete adopt evidence. Qualify isolation and receipt paths; never advertise check as a read-only export.
- **Reachability versus complete proof:** existing full trace validates directed sink coverage and confirmed relations, not every binding/scenario/test/gate pairing or passing runtime verdict. A shortcut, missing binding or unrelated test can otherwise produce misleading coverage.
- **Native HLV format lacks full identity/provenance:** flat mapping arrays and check's aggregate diagnostics cannot establish per-test/per-gate execution, occurrence pairing or Git/Model freshness. Explicit mapping and independent terminal receipts are necessary; unknown stays unverified.
- **Requirements authority:** HLV maps contain statements, while OpenSpec owns selected requirements. Read-only alias reconciliation avoids duplicates; no automatic writer can fix conflicts under this design. Projects needing initial HLV artifacts require a separate explicit owner action.
- **Version drift:** Context7/master/latest release and the installed supported binary differ. Tool version, command-contract version, native schema version, bridge version and Lekalo family versions are independent. Exact pins must be refreshed and qualified together; no semver optimism.
- **Privacy and evidence fidelity:** code-only public summaries preserve codes but can lose subject association; hashing does not remove sensitivity. Keep safe qualified local refs, explicit redaction gaps and original severity; do not scrape private diagnostic prose to recover missing mapping.
- **Policy mismatch:** current required-provider warning gates do not block, and trace operations are excluded from aggregation. Required bridge completeness needs an explicit proposed check/policy rather than relying on HLV severity or exit alone. Optional HLV must preserve standalone usability while exposing degradation.
- **Custody and freshness:** mapping is configuration, composed trace is direct evidence, QA summary is derived evidence, and HLV/native output has its own owner. Similar filenames do not grant authority. Source mutation, stale scopes and later failures must invalidate reuse without deleting independent evidence.
- **Snapshot fidelity and execution limits:** a copied project may omit dependencies, services or environment identity and falsely appear compatible; tests may produce native side effects. Unsupported execution recipes must refuse. Process-tree kill behavior and source-write canaries require real platform tests, not fake adapter assurance.

Proposed implementation sequence: qualify the Extension consumer of #34 and evidence successors; close explicit mapping/profile semantics; implement pure join/gap/conflict assessment and neutral composition; qualify isolated HLV execution/receipt provenance; wire lifecycle freshness and independent evidence custody; add real greenfield/adopt and failure-isolation E2E gates. A structural exporter or a fake-provider PASS alone does not complete issue #35.
