Every newly admitted waiver has a bounded deadline, review source, approval reference, accepted risk and exact validity pins. Missing, expired, stale or ineligible acceptance restores the underlying gate behavior. No waiver grants execution, ownership, classification lowering or public export permission.

## Proposed command/report schema

### Proposed ownership and one-store decision

**Proposal:** `crates/lekalo-core/src/waivers/` owns bounded decode/canonicalization, exact selectors, validity, eligibility, application, audit and governance comparison as pure services. CLI input/output and controlled file writing live in proposed `crates/lekalo-cli/src/waivers.rs`. The AI-lint caller delegates to this same service after producing its raw findings. It does not retain a second matcher; other producers supply admitted typed facts through explicit adapters.

Choose one canonical project store, proposed `lekalo/waivers.json`, separate from Model definitions and `.lekalo/cache/**`. It is user/repository governance input that must be reviewed and committed, with Lekalo as proposed canonical artifact owner. Proposed artifact kinds `lekalo.waiver-store` and `lekalo.waiver-audit` need exact authority/privacy classification and path admission; derived audit storage may use proposed `.lekalo/waivers/audits/**`. Add the canonical/runtime homes to both structure implementations as part of future delivery. The current authority/structure contracts do not already authorize these homes/kinds.

Per-family documents would avoid one shared configuration surface, but duplicate expiry/matching/history and allow hidden union/order-dependent suppression. Reject that design. Use a reviewed successor **`contracts/ai-lint-waivers.schema.v<V>.json`**, with the existing `dev.lekalo.ai-lint-waivers` family identity and a generalized governance title. Its historical name is acceptable; introducing `waivers.schema` with a second authoring/matching format is not needed. Proposed companion **`contracts/waiver-audit.schema.v<V>.json`**, identity `dev.lekalo.waiver-audit@<V>`, is a derived report, not another store. A governance diff is a closed report projection within that family, not an untyped diagnostic extension.

The successor is a breaking **shape** change under the existing product-version convention, not an in-place additive edit to closed `0.6.4`. It replaces singleton `configRef` with typed sorted family configuration refs and exact effective architecture/target profile refs; old `configRef` retains its old meaning only in the frozen decoder/migration. Each generalized entry has a tagged selector (`rule` or `capability`), typed scope, deadlines, approval and validity history. Preserve existing ID/reason/owner/condition concepts and the original legacy digest in migration provenance. Legacy `ruleId`, `subject`, `target` and `conditionDigest` are mapped explicitly, not guessed from a symbol or renamed to a different meaning.

Migration reads the exact frozen #76 wire through its decoder, then emits a reviewable successor candidate. Preserve dated `expiresOn` as an inclusive UTC end-of-day deadline; preserve known `sourceDigest` as a legacy source pin **without** upgrading it to a verified adapter/revision tuple. New mandatory fields absent in the old document remain visibly unresolved until supplied/reviewed. Unknown expiry is `ungoverned`, not automatically active under #88. Do not invent `createdAt`, approver, risk, source issue or authenticity from `owner`/Git history. The frozen legacy behavior stays available to explicitly pinned legacy consumers; the generalized implementation rejects a mixture of two input stores and does not silently union legacy and successor exceptions. Existing #76 goldens remain frozen; new migration fixtures demonstrate the boundary and reapproval requirements.

### Proposed CLI surface and write boundary

All commands/flags here are proposed; `--json` uses the existing global output convention. Example paths and identities are synthetic. A list can inspect syntax without producing an effectiveness verdict; an audit needs pinned profile/current facts and an explicit evaluation time.

```sh
# Proposed read-only listing and evaluated audit.
lekalo --json waivers list --store lekalo/waivers.json
lekalo --json waivers audit --store lekalo/waivers.json --profile contracted-standard \
  --as-of 2026-10-04T00:00:00Z --facts review-facts.json --check

# Proposed add previews a candidate and exact before/after plan; it writes nothing.
lekalo --json waivers add LEK-CONTEXT-006 --symbol planner.sync \
  --id waiver.planner.sync.20261004 --target model --profile contracted-standard \
  --owner planner-maintainer --approver architecture-reviewer \
  --reason "Accept the bounded gap until the tracked replacement lands." \
  --source-issue ichinya/lekalo#88 --risk correctness \
  --expires 2026-11-01 --as-of 2026-10-04T00:00:00Z --facts review-facts.json

# Proposed explicit write re-evaluates the same add operands and exact plan.
lekalo waivers add <same operands> --apply sha256:<reviewed-plan-digest>
```

`LEK-CONTEXT-006`/`planner.sync` preserve the issue's illustrative command, not a claim that the chosen current fixture contains that pair. `add` resolves a stable diagnostic code to one active registry rule ID, or accepts an explicit `--capability <id>` mutually exclusive with a rule. Capability identity includes definition version and provider/target/profile identity. It must bind an actual admitted finding/gap and condition digest from facts; a CLI label alone cannot create acceptance of arbitrary future events. Authoring resolves safe selector grammar before reading project data, requires a live full semantic identity for saved scope, and refuses ambiguous/historical-alias selection. Multiple occurrences require an explicit bounded reviewed manifest, not first-match selection.

`list` is an inventory projection, read-only. It exposes safe ID, selector, owner/approval refs, deadline and replacement links; full reason is local-only and opt-in. It does not label a waiver active without current evaluation inputs. `audit` evaluates the selected inventory and includes unexamined entries explicitly. Missing facts may yield `unverifiable/unexamined`; they never make a waiver effective. `--check` evaluates audit hygiene only under the pinned policy; a read-only audit does not execute native gates, launch adapters, access network, commit, renew, delete or rewrite the source store.

`add` defaults to stdout candidate/plan, requiring all governance fields and current eligible facts. An explicit `--apply` form may write **only after future artifact/home admission** and exact before-state validation. Borrow the lock-update design: project-root physical containment, no links/reparse points, exclusive guard, bounded stage in the same directory, canonical bytes, atomic replace and post-read verification. A changed store, profile, facts or authority pin invalidates the plan; concurrent apply cannot overwrite another review. The command neither stages nor commits Git nor writes HLV/OpenSpec/AIFHub state. Local modification is a candidate until the configured repository review authority accepts its exact content; a caller-supplied `--approver` string is metadata, not proof of approval. Approver attestation/accepted review refs must be supplied by the owner through a typed trusted seam; no forgeable `approved:true` field can authorize elevated acceptance.

Proposed defaults preserve existing command status: read-only valid listing/audit exit 0; malformed input/store/overlap exit 1; explicit pinned policy denial exit 3 with complete audit; unavailable required current input exit 4; unsupported contract/profile version exit 5; ordinary CLI misuse follows existing usage handling. Expired/stale entries do not independently make advisory audit fail. They stop applying, and the original producer/gate computes its own status. `audit --check` may separately deny hygiene only if policy explicitly requires a reviewed inventory. Never translate invalid, denied-security, missing execution or unsupported-version facts into a successful tool execution.

The successor uses closed camelCase wire fields, while preserving the issue's field meanings. Every reference has an exact identity/version/digest domain; hashes prove integrity/coherence, not issuer authenticity.

Proposed audit shape is closed `{schemaVersion,identity,storeRef,registryRef,configurationRefs,profileRefs,authorityRef,asOf,currentInputs,scope,entries,findings,changes,summary,gate}`. `storeRef` binds canonical stored content; `entries` records lifecycle/effectiveness, matched IDs, exact mismatched pin names, all reason codes and replacement links. `findings` is an immutable fact view plus a separate `gateDisposition` containing original outcome, effective outcome and exact `waiverRef {id,storeDigest,entryDigest,approvalRef}` or a state-only absence. It includes raw fact digest and current resolved severity/waivability policy pin. The summary preserves `raw,active,waived` alongside active/expiring/expired/stale/unverifiable/revoked/superseded/non-waivable counts; stale/expired entry counts are not finding counts.

Illustrative proposed **audit entry fragment**, syntactically JSON with intentionally unresolved digest placeholders; it is not a `0.6.4` schema instance:

```json
{
  "id": "waiver.planner.sync.20261004",
  "status": "stale",
  "effective": false,
  "reasonCodes": ["waivers.fingerprint-changed"],
  "deadline": "2026-11-01T23:59:59Z",
  "matches": ["finding.planner.sync.context"],
  "mismatchedPins": ["adapter.bundleDigest"],
  "storeRef": {"digest": "sha256:<store-digest>"},
  "approvalRef": {"id": "review.planner.88", "digest": "sha256:<approval-digest>"}
}
```

Existing `Diagnostic` is immutable registry-backed fact data. **Proposal:** keep disposition in the generalized report and a reviewed CI check/case disposition successor, rather than encoding it in `metadata`, rewriting `severity`, dropping diagnostics or abusing `Status::Valid`. If all raw facts are exposed in a shared envelope in future, its consumers must read gate disposition rather than infer failure from any raw error; closed diagnostic/report schemas and consumers need coordinated review. For current #76 compatible outputs, keep `report.findings` complete and explicitly document its active-only envelope projection; new automation must consume the report's exact waiver links. Fact presence, evidence coverage and gate acceptance stay separate in text, JSON, JUnit and SARIF.

## Proposed check definitions with data sources

### Proposed exact scope grammar and matching

All six scope kinds select exact admitted identities, never a glob or fuzzy string. A scope has one primary kind and explicit project/target/profile qualifiers; qualifiers are intersected, not alternatives. Store identity is bound to its project context, not inferred from where an arbitrary file happens to be copied.

| Scope kind | Data source and proposed membership rule | Leak-prevention requirement |
| --- | --- | --- |
| Project | Accepted project ID from compilation; selected rule/capability and target/profile remain mandatory. | Does not mean `*`. Require explicit broad-scope permission, cardinality bound and an approved exact occurrence manifest; new occurrences invalidate that manifest. |
| Module | Accepted semantic module ID and IR definition ownership, using the existing module selector vocabulary. | No folder/prefix/recursive module-name matching; imported dependencies are not module members. Snapshot exact eligible occurrences at approval. |
| Symbol | Current full semantic ID from accepted definition index, with current observed binding for native facts. | No short-name matching, aliases, suffixes or string prefixes during application. Different native facts for one symbol retain their exact occurrence/condition pins. |
| Path | Exact safe project-relative logical POSIX path from admitted source map/evidence; physical confinement through `ProjectFs` for reads. | No directory glob, case-folding, basename, separator guessing, URI/drive/UNC or traversal. Path relocation/identity/fingerprint change becomes stale, not a new binding. |
| Target | Exact target identity plus provider/adapter pins and current capability evidence. | No cross-target fallback or `cross-target` pseudo-target expansion; aggregate cross-target findings require their own explicit exact identity/manifest. Broad inventory requires elevated policy. |
| Profile | Exact resolved architecture profile identity/version/digest, plus separate target-profile pins where relevant. | Not every similarly named profile or inherited child; effective inheritance pin change is policy change and re-evaluates eligibility. Prefer v1 forbidding all wildcard syntax (`*`, `**`, `?`, regex/pattern objects) outright. A broad **named** project/module/target/profile scope is different from a wildcard but still needs explicit policy permission and exact occurrence manifest. A later elevated wildcard mode would require its own reviewed contract, scope ceiling, issuer evidence, deadline and expanded-member digest; it is not a hidden flag in this proposal. An explicit bounded array of exact occurrences is acceptable, with duplicate/conflicting entries rejected.

Matching order: strict schema and identity admission -> project ownership and current effective profile -> rule/capability identity -> primary scope plus every qualifier -> exact occurrence/condition -> validity pins/deadline/history/approval -> profile eligibility -> disposition only. A report's absence of a fact does not mean the waiver is valid; incomplete/unselected input is unexamined/unverifiable, complete selected input with no matching fact is orphan. Overlapping effective entries for one occurrence refuse rather than choose first/last order. Registry aliases, presentation text, severity words and location similarity cannot match an exception.

Capability gaps are admitted typed source facts such as required unsupported coverage under a pinned capability definition/provider. A waiver can temporarily accept an eligible **policy requirement** for that exact gap. It cannot make an adapter support the capability, start an operation requiring that capability, bypass transport preflight/confinement, or fill missing execution/coverage with a pass. Existing mandatory AI-lint coverage may still deny after every finding is waived; capability-row acceptance needs a separately implemented producer adapter and explicit profile policy.

### Proposed expiry, invalidation and supersession semantics

**Proposal:** core always receives one explicit whole-second UTC `asOf` timestamp; no system clock, local timezone or implicit frozen default participates. CLI `--expires YYYY-MM-DD` is authoring sugar for that date's `23:59:59Z`, preserving #76's inclusive date semantics. A deadline is effective through equality and dead when `asOf > deadline`; earliest known expiry/review deadline wins. Reject nonexistent dates, invalid timezone/fraction spellings, empty deadline sets, `createdAt > deadline`, or evaluation before creation. A review deadline cannot renew itself. Expiring means still otherwise eligible and `deadline <= asOf + profile.expiringWindow`; the window is a pinned nonnegative whole-second value.

Explicit-time reproducibility alone cannot stop CI from replaying an old date. The CI/harness owner must supply the current evaluation point from its trusted clock/run envelope, retain it in evidence and enforce an allowed timestamp age. Historical replay is explicitly labeled replay and cannot satisfy a current done gate. Local offline audits can evaluate arbitrary declared dates without claiming current approval. Clock rollback/unavailable current-time authority refuses current mandatory acceptance; it never extends a waiver silently.

Use one shared validity predicate for list-with-evaluation, audit and application, following the classification grant precedent. Every entry reports all relevant reasons; choose a deterministic headline status with dominance: invalid/non-waivable -> revoked/superseded -> expired -> stale -> unverifiable -> orphan/unexamined -> expiring -> active. Only active/expiring entries with complete approval and exact matches may apply. Unexamined is a report-selection state, not a finding of stale evidence. Missing required current pins is unverifiable; unequal known required pins is stale. No lower-confidence inferred identity gets promoted by accepting its risk.

Pin invalidation is explicit profile policy: default requires equal known condition, Model/IR content, effective architecture/target profile, family configuration, relevant source-content revision and selected adapter manifest/bundle/capability fingerprints. Pure Model findings carry a typed not-applicable adapter dimension, not unknown or a fabricated adapter hash. Policy may allow a **declared** scoped content-revision recipe instead of the whole Model/source snapshot; the recipe/version and exact selected-member digest are themselves pins. A changed policy/required pin set cannot be treated as compatible simply because the finding code is unchanged. A permissive revision policy must still retain the changed creation/current provenance and all required exact matches.

Avoid self-invalidating/circular fingerprints. Record Git creation/current commits as provenance, but default validity uses the rule's exact source-content revision projection excluding the waiver document and its own lock governance pin. Otherwise committing a waiver changes HEAD and instantly invalidates it, or the lock/store digest refers to itself. If a profile insists on strict revision equality, define that revision as a separately pinned code-input tree/owner revision before the governance-only commit; governance-only edits are compared independently. Do not falsely call this equality of arbitrary Git HEADs. Model/adapter/source changes must still invalidate according to the selected recipe. A full lock digest including the waiver store pin is an evidence ref, not part of the store's self-referential validity hash.

Revocation/supersession never rely on cache contents. The committed store retains prior immutable entries and explicit lifecycle events. A replacement has a fresh stable ID, new approval/deadline/fingerprints and an exact `supersedes` link; the predecessor remains inspectable and ineffective. Reject dangling links, cycles, duplicate IDs, competing successors and reactivation without a new reviewed entry. Deleting a committed entry stops application and is visible as a removal/revocation candidate in governance diff; audit must not claim an omitted historical row never existed. Git history/diff is the review record, while source approval references establish acceptance. Removing an audit record does not restore a revoked waiver.

## Proposed determinism strategy

**Proposal:** the input tuple is admitted raw facts, normalized project/source inputs, exact registry/family configuration/effective architecture and target profiles, governance store, authority/approval receipts, validity recipe and explicit evaluation time. Supersession links retain explicit predecessor relation; no input array order selects the effective waiver. Stable waiver identity is explicit and persists across audit runs; raw finding identity remains the producer's, with condition and input pins distinguishing changed facts. Waiver reason/deadline changes may change store/entry/audit digests but cannot change raw fact digest, severity, evidence, capability support or metric vector. Report `raw = active + waived` must hold for eligible finding rows; coverage/gap and inventory counts have their own separate arithmetic. Regression baselines compare raw measurements; removing active gate warnings by adding waivers is acceptance broadening, not improved architecture metrics.

Index by project/selector/scope/target/profile/occurrence rather than scan every waiver against every finding. ## Proposed profile format and non-waivable policy

**Proposal:** #84 owns the architecture profile's effective rule severity, required evidence and measurable reason for blocking; #88 owns exact exception validity/application. ## Risks

- **Duplicated exception authority:** a generic store beside #76's ignore wire creates inconsistent matching/expiry. One successor, explicit migration and common matcher prevent order-dependent acceptance; frozen legacy consumers remain explicitly pinned.
- **Profile dependency:** #84 is open. Hardcoded warning/error eligibility or invented security tags would silently diverge from its catalog and inheritance. Consume the resolved effective profile and keep unknown eligibility ineffective.
- **False proof:** accepting a diagnostic/capability gap can be mistaken for passed execution, supported capability, complete coverage or safer Model. Preserve raw facts, required-evidence gaps and original outcomes; acceptance is a separate policy result.
- **Deadline replay:** pure explicit-time audit supports reproducibility but cannot authenticate "now". Current CI needs trusted evaluation-time custody and replay labeling; no silently frozen date may keep expired acceptance alive.
- **Fingerprint breadth/circularity:** global Model digests can cause frequent reapproval; permissive scoped recipes can miss changes. Pin the exact recipe/member manifest and exclude only explicitly separated governance self-pins, retaining real code/adapter changes.
- **Scope expansion:** a named module/project can be broad even without `*`. Typed membership, approved occurrence manifest, cardinality and issuer policy must prevent new/unrelated findings acquiring old acceptance.
- **Approval authenticity:** reason/owner/approver text, Git presence and matching hashes are not issuer verification. Elevated policy needs an admitted authority seam; missing proof remains unverifiable, not auto-approved.
- **History tampering:** in-place renewal, deleted prior IDs or cycles can disguise permanent risk. New replacement IDs, retained lifecycle, governance diff and exact done pins are necessary; local audit deletion cannot resurrect acceptance.
- **Visibility mismatch:** #76's report retains waived findings while its envelope omits them; existing CI projections have no waiver link. Consumer schema/projection updates must be coordinated and preserve fact/status versus disposition distinctions.
- **Privacy leakage:** reasons, reviewers and source decisions can expose consumer identities. Committed storage and external provenance have separate privacy eligibility; hard export/leak/tenant/consent enforcement remains binding.
- **Authority/layout drift:** proposed canonical/runtime homes and artifact kinds are not admitted today. A future `add --apply` needs coordinated custody/structure changes and race-safe atomic writing; stdout candidate can be implemented independently.
- **Merge/acceptance drift:** preserve the current registry union and frozen wire versions, recheck #84 and shared pins on the merged revision, and distinguish synthetic neutral provenance tests from actual HLV/AIFHub consumer acceptance.

Proposed delivery stages: admit successor/audit/policy/authority homes and migration rules; implement pure scope/validity/history/admission; delegate #76 matching and add read-only list/audit; implement reviewable add plan and governed atomic apply; wire lock/governance diff/CI/done and neutral provenance; finish profile-owned non-waivable and all seven AC fixtures on the merged #84 candidate.
