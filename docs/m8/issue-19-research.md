## Proposed command/report schema

### Command and ownership

Proposed commands preserve the three issue examples exactly and use the existing global JSON option in either position:

```sh
lekalo portability
lekalo portability --from node-typescript --to php-laravel
lekalo portability --to go-service --json
lekalo --json portability --project examples/planner --from node-typescript --to php-laravel --targets config/portability-targets.json --evidence reports/portability-evidence.json
lekalo portability --from node-typescript --to go-service --symbol planner.schedule_calculate --check --json
```

Proposed flags: `--project DIR` selects the existing project root; `--from TARGET` selects a source target; `--to TARGET` selects one destination; `--targets PATH` selects the closed target-binding configuration; `--evidence PATH` supplies qualified recorded semantic/adapter/implementation/scenario evidence; `--symbol ID` and `--module ID` are mutually exclusive optional scopes; `--check` makes unresolved required obligations, blockers and declared behavior loss deny. No scope means the entire project. JSON is global, not a second per-command format contract.

Proposal default configuration home is exactly project-relative `config/portability-targets.json`, outside reserved `lekalo/**` and `.lekalo/**`; explicit `--targets` overrides that location. No recursive search, environment-selected executable or product-name fallback. This is an explicit user-toolchain input, not a new canonical Model home. The configuration specifies optional `defaultSource`, optional `defaultDestinations`, target-to-exact-profile bindings and recorded evidence references. If `--from` is absent, use its `defaultSource`, otherwise the sole declared project target; multiple candidates refuse with an actionable ambiguity diagnostic. If `--to` is absent, use `defaultDestinations`, otherwise all other configured targets, sorted. With no destination configuration, the bare command emits structural inventory plus an explicit destination-evidence gap and no fabricated supported destination. An explicitly selected unknown target ID is invalid. A configured Go target with an accepted profile and no adapter snapshot is an assessable **unknown**, not an unknown selector or an unsupported adapter.

Proposal core ownership: `crates/lekalo-core/src/portability/{mod,request,requirements,assess,planning,wire,canonical,diagnostic,version}.rs`. Typed `assess` receives validated compilation, graph, attachments, exact target snapshots and bounded request; it performs no filesystem/process/network operations. CLI `crates/lekalo-cli/src/portability.rs` owns classified reads, duplicate-key-safe parsing, safe project-relative selectors, lock/input pin verification and human/JSON rendering. Prefer existing immutable implementation/profile/storage projections and producer validation rather than reimplementing their parsers or validators.

Proposal assessment consumes recorded discovery evidence by default and launches no adapter, native test, generator, scanner or provider. Snapshot origin/trust/currentness must be stated. Fresh live collection can be a later explicitly authorized capability-discovery command; this issue needs exact qualified input provenance, not a hidden process side effect. Existing protocol schemas and operation enums need no change if this boundary is retained.

All schemas are closed Draft 2020-12 at nested object/union boundaries and reject duplicate JSON keys in production ingestion, unknown members, contradictory state payloads, missing pins and invalid arithmetic. Report binds the recipe schema/instance digest; target, profile, component/capability definition and adapter versions are independent exact pins, not uniformly rewritten as `0.8.0`. Ordinary Model/IR, graph/effects, implementation, target-profile, storage-engine and diagnostic item contracts remain frozen if their actual wire shapes do not change. Do not insert new report members into frozen diff, provider, history or CI schemas. Advertising the command through an existing closed provider manifest is a separate reviewed `0.8.0` successor plus consumer gates; no automatic history recording/export is necessary for #19.

Proposal report fields: `{schemaVersion, identity, recipeRef, projectRef, scope, source, destinations, inputs, coverage, subjects, summaries, migrationSurface, affectedScenarios, affectedGates, diagnostics}`. `projectRef` binds project ID and exact Model/IR semantic content; consumed source-bearing/detected evidence receives separate digests. Each destination binds target ID, resolved profile ID/version/digest/sourceDigest, all component definition versions, capability-definition identities, adapter identity/version/protocol/capability digest or an explicit availability state, and storage profile refs where applicable. Record lock digest and evidence trust/freshness separately.

Each subject row names typed `kind:id`, optional typed member, dimension, requirements, required/offered policy, classification, verification state, binding kind, blocking state, producer reason/evidence refs and witness paths. State alternatives are closed tagged unions: `portable`, `supported-with-mapping`, `partial`, `target-specific`, `unsupported`, `unknown`; verification is orthogonal (`untested`, `recorded-pass`, `recorded-fail`, `not-applicable`). Availability/currentness/trust are explicit. A `supported-with-mapping` row means the pinned semantic mapping covers the declared obligation with stated conditions; it is not a native-equivalence verdict. Lossy mappings are `partial` or `unsupported` for the affected obligation and carry a behavior-loss warning; they cannot be counted as fully portable.

Proposed migration rows are stable IDs linking subject/member, dimension, reason, required capability or replacement implementation, relevant source/destination bindings, prerequisites, scenarios, gates and evidence still needed. Actions are advisory fixed kinds such as `implement-hook`, `replace-mapping`, `review-storage-policy`, `bind-target`, `verify-scenario`, `collect-evidence`. No script/command execution payload, time quote, code edit or data migration is authorized by a row. Human output groups blockers, partial mappings, custom/foreign/external obligations, behavior loss and unknown verification; it displays the four risk summaries before any optional overall ratio.

## Metric definitions with data sources

### Requirement extraction and conservative classification

Proposal unit: each eligible semantic definition is one subject; fields/effects/attachments are obligation rows under that subject. Exclude project/module containers and native target-binding metadata from the portable-business-symbol denominator, while inventorying them separately. The versioned recipe defines every admitted definition and attachment kind; an unimplemented applicable kind is an explicit extraction gap, never silently absent. Traverse required type/reference/operation dependencies with bounded canonical witnesses; importing a module does not mean every unrelated definition is required.

| Dimension / output | Proposed source and decision |
| --- | --- |
| Structural portability | IR types, explicit references, visibility/portability annotations and transport/type projection obligations. An abstract type contract may be structurally portable while its storage/behavioral rows remain partial or unknown. |
| Behavioral portability | Input/output/error contracts, invariants/transitions, query semantics, declared effects, transaction grouping and exact hook implementations. A hook with no destination implementation is a blocker for that operation; merely declared foreign/custom presence stays untested. |
| Storage portability | Storage/query attachments, engine profiles, precision/scale/rounding/null/order policies, relations and transaction isolation guarantees. Compare required policies against offered ones; a reused database component does not automatically cover an unsupported projection or isolation requirement. |
| Operational portability | Extended event/job/external/cache/publication effects, retry/idempotency/ordering/delivery/atomicity requirements and applicable NFR/authorization/classification constraints. An observed implicit hook must retain its inferred status and proof gap, even if a declared explicit replacement could address it. |
| Custom implementations | Reuse `implementation::validate` then `implementation::portability`. List generated/custom/foreign/external/unsupported/missing separately by hook and target; preserve ownership and covering scenarios. Destination absence in a complete applicable implementation inventory is a blocker; absence of that inventory is unknown. |
| Behavior-loss warnings | Exact required/offered semantic policy mismatch and bounded producer evidence: decimal policy differs; required isolation not guaranteed; required observer hook unsupported. No warning based only on target names. |
| Estimated migration surface | Unique changed/missing hook implementations, mapped symbols/members, storage objects requiring review, affected scenarios/gates and unresolved obligations, with overlap reconciliation. Counts are planning estimates under the recipe, not LOC/person-hours or proof of minimal implementation work. |
| Affected scenarios/gates | Direct scenario coverage plus typed dependency/effect witnesses and qualified trace joins. Separate affected/required/planned/executed states; missing trace/native mapping yields unknown gate coverage. |

Proposal precedence is by obligation, preserving mixed risks: explicit incompatible/unsupported required semantics => unsupported blocker; known restricted coverage/loss => partial; target-specific implementation/declaration => target-specific risk with explicit replacement obligation; qualified full declared requirement coverage => portable or supported-with-mapping; absent, stale, insufficiently trusted, unmapped or unknown capability => unknown. Keep a target-specific risk tag even when a replacement mapping exists. A subject summary can name the most severe known blocker but must retain all dimension rows, additional unknowns and verification states. Explicit full profile support combined with adapter unknown/unsupported cannot yield full execution support. Lack of a provider in the profile's closed complete capability declaration is an unsatisfied declaration; it is not proof that an uninspected native runtime cannot implement the capability.

Different capability namespaces must be bridged by reviewed semantic mapping definitions. For example `runtime.async`, `storage.transactions` and `verify.operations` describe different promises; none is an alias for required isolation, task delivery or arbitrary custom-operation semantics. Each mapping names exact definition versions and preconditions. Required semantic capabilities not currently represented by an owner registry remain unknown until a reviewed `0.8.0` definition/mapping is published; do not stretch an existing broad definition. Per-symbol adapters may contribute bounded namespaced facts only through the evidence schema and known recipes, never arbitrary verdict-authoring prose.

### Counts, percentages and scope

Proposal per-dimension mutually exclusive primary class counts partition all eligible applicable subjects: portable, supported-with-mapping, partial, target-specific, unsupported, unknown. Non-applicable rows have a separate count and never improve the numerator. A ratio publishes integer numerator/denominator, explicit inclusion recipe and rounding rule; denominator zero means unknown/not-applicable, not 100%. `structuralPortable = portable / eligibleApplicableSubjects`; mapped support is separately displayed and never silently added. No overall weighted percentage is required. If a convenience total is supplied, compute the intersection of fully declared-supported dimensions across unique subjects and label its basis, with blockers/unknowns/custom obligations beside it. The issue's illustrative `Portable: 84%` is not a fixture measurement or mandated value.

Selected symbol/module reports include cross-boundary dependency witnesses and required affected scenarios/gates while counting selected subjects separately from support dependencies. Avoid double-counting one custom hook, shared storage object or gate reached through several paths. A truncation/unsupported extraction recipe makes affected totals incomplete with a known lower bound; a known blocker stays visible alongside unknown remainder. Ratios for complete data never borrow lower-bound totals.

## Determinism strategy

Proposal canonical output is compact UTF-8 JSON with sorted object keys, byte-sorted set-like identities and deterministic witness tie-breaking. Bind report identity to Model/IR pins, recipe, explicit scope, declared/effective target profiles, adapter/capability definitions, storage policies, lock selection and every consumed evidence artifact. Exclude wall-clock timings, absolute paths, unordered native output and discovered host state from canonical assessment. Expiry/freshness decisions use an explicit recorded evaluation context, not hidden current-time reads; evidence carrying expiry without that context is unqualified.

Proposal reuse indexed graph/effect adjacency and deduplicate typed requirements before comparing targets. Share repeated dependency work across symbols/targets. Initial recipe bounds are explicit reviewed limits: 50,000 selected subjects, 256 traversal depth, 250,000 dependency edges, 1,000,000 obligation rows, 32 MiB per report and 10,000,000 deterministic work units. Validate limits before allocation and integer operations. Exhaustion emits incomplete coverage and refuses full counts/ratios; never claim a clean truncated assessment. Input byte limits and safe filesystem containment are enforced before parsing, including Windows reparse points/symlinks and non-UTF-8 input.

Proposal tests permute source/target declarations, attachment collections and graph insertion order, compare repeated live CLI bytes across supported OSes, and change one profile/definition/evidence pin at a time to prove report identity changes. A formatting-only source edit preserves semantic results, while separately source-bound evidence can become stale. Invalid Model/IR/attachment pins propagate producer diagnostics with no fabricated partial success.

## Diagnostics (LEK-PORT-*) proposal

Candidate codes below have no collision in the inspected registry artifacts; they are not reservations. Register the family in the reviewed M8 union successor, preserve both existing `0.6.4` and `0.6.5` entries and tombstones, and explicitly select the new registry in the new producer. Frozen predecessor outputs retain their pinned registries. Update dependent validation profile/registry schema pins only where consumers actually change, with `0.8.0` successor artifacts rather than editing accepted contracts in place. Keep `diagnostic.schema.v0.2.16.json` if item shape is unchanged.

| Proposed ID / code | Trigger, severity and allowed envelope statuses |
| --- | --- |
| `portability.input-invalid` / `LEK-PORT-001` | Malformed configuration/evidence, duplicate keys, invalid scope/target choice or arithmetic; error, invalid. CLI syntax itself retains `cli.usage`. |
| `portability.version-unsupported` / `LEK-PORT-002` | Unsupported portability recipe/report/evidence contract version; error, unsupported-version. Existing profile/protocol producer refusals preserve their own codes/status. |
| `portability.evidence-incomplete` / `LEK-PORT-003` | Missing/stale/untrusted capability, attachment, implementation or scenario/gate coverage; warning, valid/denied; fixed gap reason and explicit unknown state. |
| `portability.mapping-partial` / `LEK-PORT-004` | Qualified semantic mapping covers only part of a required obligation; warning, valid/denied; bounded required/offered policy refs. |
| `portability.capability-unsupported` / `LEK-PORT-005` | Explicit required capability incompatibility/unsupported state; warning, valid/denied; subject, dimension, capability and producer evidence refs. |
| `portability.implementation-required` / `LEK-PORT-006` | Complete implementation inventory proves missing/unsupported destination hook; warning, valid/denied; hook contract, binding kind and scenario refs. Reuse existing implementation diagnostics where already emitted. |
| `portability.behavior-loss` / `LEK-PORT-007` | Known lossy required policy mapping, such as precision/isolation loss; warning, valid/denied; exact mismatch and alternative planning-row ref. |
| `portability.analysis-incomplete` / `LEK-PORT-008` | Deterministic traversal/work/report bound or unimplemented applicable requirement extraction; warning, valid/denied; lower-bound/unknown fields remain explicit. |
| `portability.check-denied` / `LEK-PORT-009` | Explicit `--check` has required blockers, partial/lossy or unknown obligations, or required extraction/coverage gaps; error, denied; references underlying findings and preserves the report. |

Proposal diagnostic data uses closed bounded semantic IDs, fixed dimension/reason tokens, numeric counts and refs; no absolute path, raw adapter stdout, source text, secret or native foreign symbol locator is embedded in generic messages. Locations use existing logical source spans only when known; unknown span is allowed under the registered rule. Every warning carries a report reason and advisory alternative; no safe-fix ID is allocated. Ordinary analysis remains `valid` when it successfully explains a target's unsupported/unknown symbols. `--check` denies those unresolved required obligations without turning warning severity into envelope status. Configuration failure and unsupported document versions follow the existing result stream/exit contract.

## Profile format

Proposal configuration references existing target profiles; it does not introduce a competing inheritance engine or reinterpret architecture/validation policies. Each target binding names `{targetId, profileRef:{id,version,sourceDigest,resolvedDigest}, profileDocumentRef, adapterEvidenceRef?, storageProfileRefs}`. References use closed versioned digest pins and bounded project-relative artifact selections. Optional refs use explicit absence/availability unions where absence has semantic meaning. Defaults must reference unique configured IDs; duplicate bindings, ambiguous inherited selection, unknown nested keys and mismatched lock/profile pins are invalid. A bare default can resolve the sole Model target only when exact profile evidence is available, otherwise it reports the qualification gap.

Proposal target tokens `node-typescript`, `php-laravel`, `go-service` are caller identifiers used by the examples. They must resolve explicitly to profiles such as `node-postgres-http`, `laravel-postgres-http`, `go-postgres-http`; logic never switches on those tokens. Aliased/custom target names with identical pinned capabilities produce identical assessment facts apart from provenance identities. A Go target may have complete declared structural/storage profile support and unknown native execution evidence at the same time.

Proposal evidence manifest admits qualified immutable references to existing implementation/transaction/extended-effect/storage/query/scenario/trace families and recorded adapter capability snapshots. Every reference validates both schema and semantic admission before use, including project/Model/IR/scope/target/profile/recipe pins. It also declares which applicable families were inventoried completely; a missing attachment cannot be assumed irrelevant solely because no file was supplied. A partial manifest stays partial. No configuration waiver upgrades unknown to supported or erases an unsupported hook; explicit alternative profiles merely create separately pinned assessments. `--check` is an explicit fixed gate policy in v0.8.0; a richer custom portability policy is deferred until separately specified.

## Risks and proposed delivery stages

- **Evidence strength:** a declared capability, foreign binding or probe is not observed behavior. Preserve untested/unknown states and complete inventory requirements; unsupported and unknown can both block a strict plan for different reasons.
- **Registry integration:** the checkout has two explicit diagnostic generations. An M8 union must retain #84 and all predecessor families while preserving frozen output pins; shared M8 code allocation and successor ownership require reinspection on the implementing base.
- **Semantic mapping:** broad runtime/transaction/generation capabilities cannot prove precise decimal, isolation, retry or hook semantics. New definitions use `0.8.0`; absent owner definitions remain gaps. Source profile support itself may be unknown.

- **Partial evidence and scale:** omitted attachment families, incomplete traces and bounded closure can undercount migration surface. Complete inventory is required for definitive absence; preserve lower bounds and unknown totals.
- **Custody and privacy:** foreign locators, raw source, adapter output and private-project paths may reveal identities. Unchanged contracts remain frozen and optional discovery/history/diff successors need deliberate consumer coordination.
