## Proposed CLI and workflow

These are present command shapes, not newly invented flags. `PROPOSAL_ID`, `PROMOTION_DIGEST` and `NATIVE_ID` come from the respective producer. Commands are intended for a disposable synthetic project in eventual acceptance, and are not executed by this research.

```text
lekalo --json init --adopt --target node-typescript --profile default --project . --dry-run
lekalo --json init --adopt --target node-typescript --profile default --project .
lekalo --json scan --target node-typescript --profile default --project . SCANNER_PROGRAM SCANNER_ARGS...
```

Current promotion remains a reusable rendering seam; the new confirmation service adds the required complete revision binding and rollback. Confirmation of a binding alone leaves its Model definition a proposal. Native attachment and `contract check` do not establish a native run.

### Proposed new commands and exact flags

All commands accept `--project DIR` using existing root-selection/path rules, and global `--json`/`--no-cache` retain their meaning. `analyze`, `refactor`, `confirm --dry-run`, `apply --dry-run`, `rollback --dry-run` and `coverage` are read-only: output goes to stdout without hidden report/cache writes. Users may explicitly save local reports; fixtures use a harness to capture output instead of shell redirection that could leak private data.

```text
lekalo --no-cache --json adoption analyze --symbol taskboard.complete_task --target node-typescript --profile default --project .
lekalo --no-cache --json adoption analyze --module taskboard --target node-typescript --profile default --project .
lekalo --no-cache --json adoption analyze --use-case taskboard.complete_case --target node-typescript --profile default --project .
lekalo --json adoption confirm --analysis analysis.json --definition taskboard.task --binding PROPOSAL_ID --candidate NATIVE_ID --dry-run --project .
lekalo --json adoption confirm --plan confirmation.json --confirm CONFIRMATION_DIGEST --project .
lekalo --no-cache --json adoption refactor --symbol taskboard.complete_task --target node-typescript --profile default --verification verification.json --project .
lekalo --no-cache --json adoption refactor --symbol taskboard.complete_task --target node-typescript --profile default --verification verification.json --candidate candidate.json --project .
lekalo --json adoption apply --plan refactor.json --dry-run --project .
lekalo --json adoption apply --plan refactor.json --confirm REFACTOR_DIGEST --project .
lekalo --json adoption rollback --receipt apply.json --dry-run --project .
lekalo --json adoption rollback --receipt apply.json --confirm ROLLBACK_DIGEST --project .
lekalo --no-cache --json adoption coverage --symbol taskboard.complete_task --project .
lekalo --no-cache --json adoption coverage --module taskboard --project .
lekalo --no-cache --json status --adoption coverage.json --project .
lekalo --no-cache --json impact taskboard.complete_task --adoption coverage.json --project .
lekalo --json trace query trace.json gaps --adoption coverage.json
```

**Proposed selection rules:** exactly one `--module`, `--symbol` or `--use-case` for analyze/coverage/refactor, with refactor's module/use-case alternatives following the same grammar. An observed symbol may lack a canonical definition; use its stable observed ID, not a guessed canonical match. A use-case ID is an explicitly reviewed scope record linking one endpoint/scenario/root symbol; if it is unknown, show candidates and require a scope definition rather than scanning all code by default. Module scope is exact, without wildcards or implicit project expansion. Necessary dependency reads are named separately from the mutation set. Adapter read scopes must be intersected with privacy/exclusion grants; selecting a symbol after an overly broad scan is not proof of scoped access.

**Proposed confirmation rules:** `--definition ID` is repeatable for an explicit reviewed set; an optional `--binding PROPOSAL_ID` and `--candidate NATIVE_ID` resolve that definition's native identity. A Model-only definition can be confirmed without granting a native binding or conformance claim. Dependencies not already canonical must be separately selected or remain unresolved/blocking; never auto-confirm a whole inferred closure. Preview consumes `--analysis` and explicit selections; apply consumes `--plan --confirm`, mutually exclusive with preview inputs. Reject mixed/omitted actions before any write. Refuse stale analysis, duplicate IDs and incompatible existing definitions.

**Proposed recommendation rules:** no `--candidate` means advisory recommendations only; a plan without concrete writes cannot apply. `candidate.json` is a closed patch document containing exact bounded file before/after bytes or content-addressed payload references, not executable commands. Candidate origin is a qualified adapter or a supplied reviewed patch, explicitly recorded. Transformations unsupported by the adapter are marked unsupported; future general AI refactoring is not a dependency. The same selection and all consumed pins bind advice, candidate and verification.

**Proposed projection rules:** `--adoption FILE` admits a current coverage attachment against the selected project/model/lock/source/registry inputs. It emits a new 0.8.0 wrapper with the original upstream result plus effective mode/coverage/gaps, never appending unregistered members to an old closed schema. Existing calls without that flag keep their current wire family. `trace query` retains its actual MANIFEST/SELECTOR operands; coverage binds the manifest and query result without rewriting an HLV task or the supplied manifest. Reject stale/foreign attachments, rather than silently dropping them.

The new contracted feature is authored as canonical definitions/scenarios and maintained native implementation in the explicitly selected area, then declared/attached/checked through the existing contract surface and the qualified native verification seam. No generator owns its handler body. Editing an untouched observed symbol offers the same scoped preview and permits declining it; it never forces a whole-project transition.

**Read-only analysis:** compose detected project layout and scan evidence, retaining uncertainty for dynamic behavior, unavailable adapters/native gates and missing effect/policy evidence. Unknown scan records are not empty contracts. If canonical skeleton is absent, `init --adopt --dry-run` remains the first no-write step; applying init explicitly creates the existing zero-module skeleton. Analyze proposes the first module and definitions; they become canonical only through selective confirmation. Scan may record derived evidence under its existing documented command; this is separate from analyze/recommendation commands' no-write posture.

**Exact plan lifecycle:** `proposed -> reviewed -> staged -> verified -> completed`, with explicit refused/failed/rolled-back/recovery-required outcomes. A digest identifies content; only `--confirm` of the reviewed digest plus an independently admitted write/execute scope authorizes application. Before staging and again before committing candidate bytes, re-fingerprint every consumed source/model/lock/adapter/profile/gate/evidence input. Any change requires rebuilding the plan. Even an out-of-scope source edit invalidates an old source snapshot; it does not enlarge the mutation scope or force migration.

**Apply and recovery:** evaluate bounded relative paths through existing root/no-follow rules; refuse traversal, aliases, symlink/reparse escapes, excluded files, unreviewed deletes and writes outside the exact set. Snapshot the original bytes and metadata for every intended write, including absent files. Stage the candidate in a disposable bounded copy, run admitted checks there, and journal installation into the original with per-path compare-and-swap checks. Multi-file installation must support rollback/recovery; do not claim filesystem-wide atomicity. Concurrent/dirty unrelated work is preserved. Never reset/stash/clean the repository. A partial write, failed verification, receipt write failure or cleanup defect cannot record a completed adoption.

**Rollback:** preview the exact files/Model/index/contract registry/ownership/support state to restore, including removal only of files this plan created. A rollback digest binds the apply receipt, snapshots and expected current post-state. Changed post-state from later edits is a conflict; refuse replacement and report recovery-required without destroying those edits. An interrupted apply leaves a durable discoverable journal. Keep sensitive source snapshots local under admitted runtime custody; hash-checked restoration evidence is separate from publicly shareable receipt summaries.

**Behavior preservation:** declare the obligation before any patch. Run the same pinned native baseline/candidate tests with independent expected outputs for input/output/error cases, declared read/write/event effects, idempotency/invariants and policy/transaction behavior applicable to the chosen slice. Include native typecheck/build and semantic/scenario checks where required. Require genuine execution records for both states and explicit coverage limitations; preserved behavior only means the stated obligations passed. Adapter declaration parity, fingerprints or a passing generic test suite cannot prove all runtime semantics. The synthetic fixture should include an unchanged behavior oracle that a deliberately faulty refactor fails despite passing a shallow happy-path test.

The proposed qualified verifier reuses native plan/approval/tool/refusal models but needs an actual bounded execution capability in the implementing product. Where that capability is absent, apply is unsupported/unavailable, no test is reported as passed, and AC4 is not complete. Never enable the current test-only runner through a marker/environment backdoor. Trusted fixture execution proves the synthetic scenario; private production consumers need their separately admitted execution scope and current platform confinement evidence.

**Hybrid join:** an untouched observed symbol stays source/native-test authoritative. An adapted legacy symbol is effectively contracted only after reviewed canonical semantics and a conformed maintained-code binding exist; its observed provenance can remain as history, not a second conflicting owner. A new contracted symbol has the same maintained-code authority boundary. Unknown/unbound/conflicting records remain explicit gaps. Aggregate counts use disjoint effective sets while preserving raw provenance; prefix/path order cannot choose ownership. No Model `mode` field, managed requirement or generated ownership claim is introduced.

Status displays mode/freshness/verification separately; pending/refused/failed refactors never count as completed. Impact traverses qualified cross-boundary dependencies and retains conservative observed gaps even outside the selected edit area. Trace links contracts/scenarios/native tests/gates and actual receipts, with stale and uncovered portions visible. Later `scan`, `bindings audit`, `observe check` and `contract check` can invalidate relevant evidence after unrelated changes; none launches a required repository-wide migration.

## Risks and non-goals

- **Evidence-to-contract laundering:** confidence or a confirmed location cannot establish a runtime contract. Separate binding review, canonical definition confirmation, conformance and executed preservation evidence; incomplete behavior blocks only claims/actions requiring it.
- **False verified completion:** existing native production refusal and declaration checks can look successful when only metadata is validated. Preserve execution/specification distinctions and require independent actual test/oracle receipts for AC4.
- **Revision drift and concurrent edits:** Git HEAD/index digest alone misses dirty bytes, lock/profile/adapter changes and existing Model destination edits. Revalidate complete pins and exact expected file states before mutation and finalization.
- **Partial transaction/recovery:** current promotion is not a complete source transaction. Recovery journals and selective compare-and-swap rollback must survive interruption, write errors and later user edits without broad cleanup.
- **Adapter and framework uncertainty:** the MySQL contributor scan fallback is Experimental; authored evidence is not successful scan transport. Qualify the chosen minimal scanner lane and report unsupported dynamic behavior; do not add source-language parsing to core.
- **Shared union/version changes:** registry, authority/privacy, provider discovery, optional protocol extensions and suite pins have parallel owners. Re-inspect the merged M8 base, preserve admitted producer pins and apply 0.8.0 only to changed/new families.
- **Scope and mixed ownership:** effective mode joins must not double-count histories or turn cross-boundary impact into authority to migrate neighbors. Unknown/conflicting joins are visible gaps, not first-match ownership.
- **Sensitive recovery material:** rollback snapshots contain source bytes. Local read permission and a digest do not authorize export; admit private runtime custody and publish only synthetic validation evidence.

**Non-goals:** automatic mass refactor; a full repository retro-model; generic AI rewrite/equivalence proofs; required managed mode or the complete #111 lifecycle; hidden tool/adapter installation; production provider/service execution; private consumer inspection/publication; changing untouched Model/IR/protocol/lock families; changing HLV/AIFHub task ownership or claiming their external acceptance. The tutorial may use one deterministic supplied/adapter-qualified patch; it must not imply all legacy transformations are supported.
