# Issue #74: versioned safe-fix recipes and `lekalo fix` research

Research only, 2026-10-06. Acceptance authority: [issue #74](https://github.com/ichinya/lekalo/issues/74), read live with `gh issue view 74 --repo ichinya/lekalo --json title,body,labels`. Checkout: `ichinya/m8-issue-74`, inspected HEAD `15bd13917654dc20ad19b089a5bb8e5e29c2099f`. The checkout is based on main and reports product `0.6.5`; the dispatched M8 target is product **0.8.0**. This research does not perform the product bump. Only `docs/m8/issue-74-research.md` and its local commit are delivered; no implementation, contracts, fixtures, workflows, or remote mutations are included.

Decision: add a closed, versioned recipe catalog and a typed `lekalo_core::fix` planner, delegating canonical Model mutations to #73's semantic operations. Bind every plan to exact source bytes, recipe implementation, selected operations, policy, and adapter custody. Offer deterministic preview, apply only explicit selections, keep validation inside the rollback boundary, and return a machine-readable audit receipt for success, no-op, refusal, and rollback. Adapter fixes retain their adapter namespace and cannot supply arbitrary canonical edits.

All new paths, APIs, flags, schema members, code allocations, and test names below are **proposals**. New or changed contracts take **0.8.0** in their implementation commit, including filenames, identifiers, discriminators, constants, and consumer/hash pins. Unchanged contracts retain their accepted versions and bytes, as required by `docs/versioning.md`. Recipe version is separate from the schema version; initially proposed recipes use `0.8.0` and are selected by exact version, never a floating alias.

## Proposed command/report schema

### Command selection and explicit mutation

Preserve all three issue examples as public syntax:

```sh
lekalo fix --list
lekalo fix LEK-REF-014 --dry-run
lekalo fix --safe
```

`--list` renders the versioned catalog without loading a project or writing. A positional diagnostic code filters current findings; it never identifies a file offset or grants permission. `LEK-REF-014` is currently an illustrative unregistered code: before a matching upstream rule is delivered, return the registered `fix.input-invalid` finding rather than guess an alias or allocate a reference rule in this issue. A known rule with no recipe returns explicit `not-applicable` advice and no edits.

Additional proposed exact flags and examples:

```sh
lekalo --json fix --list
lekalo --json fix --safe --dry-run --project examples/planner
lekalo --json fix --recipe core.normalize-canonical@0.8.0 --dry-run --project examples/planner --plan-output preview.fix-plan.json
lekalo --json fix --apply preview.fix-plan.json --confirm sha256:<planId> --project examples/planner
lekalo --json fix --recipe core.add-declared-effect@0.8.0 --dry-run --project examples/planner --plan-output effect.fix-plan.json
lekalo --json fix --recipe core.add-declared-effect@0.8.0 --apply effect.fix-plan.json --confirm sha256:<planId> --allow-unsafe --project examples/planner
lekalo --json fix --recipe core.add-field-metadata@0.8.0 --apply metadata.fix-plan.json --confirm sha256:<planId> --allow-breaking --project examples/planner
lekalo --json fix --recipe adapter.node-typescript.regenerate@0.8.0 --target node-typescript --dry-run --project examples/planner --plan-output target.fix-plan.json
lekalo --json fix --recover sha256:<transactionId> --project examples/planner
```

The paths above are illustrative user operands, not claims that these example projects or output files exist. `<planId>` and `<transactionId>` stand for complete 64-hex digests. Use `--recipe ID@VERSION` repeatably for exact selection, `--project DIR` for the root, `--target ID` only for an adapter recipe. Recipe-specific arguments are a closed request JSON supplied by proposed `--request FILE`; a request cannot override the recipe class, target, write scopes, or plan pins.

Mode rules: exactly one of list, preview (`--dry-run`), apply, or recovery. With no mode/selection show usage and perform no writes. A positional code without `--dry-run` is informational preview only. **`--safe` without `--dry-run` is the issue's explicit safe-batch apply request:** select only currently applicable safe recipes, compute/show the full plan, revalidate it under the transaction lock, and apply as one all-or-none batch; record the selection and results. It is never implicit in validate/doctor/generate-check. With `--apply FILE`, the file must be the exact standalone fix-plan document and `--confirm` must match its digest; apply cannot silently replan a changed source.

`--allow-unsafe` and `--allow-breaking` require exact `--recipe` selections and a bound plan/confirmation; neither widens `--safe`. Breaking permission does not grant unsafe permission implicitly. Unselected plan entries, conflicting selectors, a target argument on a core-only recipe, missing request fields, and unknown flags fail before any source write. Mixed unsafe/breaking batches require every entry to be selected and its class permitted. Manual-only recipes can be listed/explained, never applied under any flag. `--recover` restores verified before-images of an unfinished local transaction, never applies a fresh recipe; refuse recovery while its writer is live.

Preview writes no source, cache, history, backup, or lock state. Explicit `--plan-output FILE` permits only that separately selected, bounded, nonoverlapping output; absent the flag, the preview exists solely in stdout. Deny output collisions with input/source/lock/history/transaction state and symlink/reparse destinations. Human preview includes recipe IDs/versions, class, exact affected paths/symbols, preconditions, semantic/file diffs, and blockers. JSON and human views derive from the same typed plan. Apply must not suppress its audit result; an output failure remains nonzero and is distinguishable from an already committed transaction in durable local state.

## Recipe classes and goal decomposition

Class is a maximum-risk declaration that actual diff/policy may **raise**, never lower. Safe requires evidence that public behavior/contracts/storage/wire semantics are unchanged; empty semantic diff alone cannot certify target runtime behavior. Unsafe permits implementation-semantic change with public compatibility still evaluated. Breaking covers contract/storage/wire changes, including adding an effect to a declared public contract. Unknown or incomplete compatibility is manual-only/blocked until evidence or explicit classified operation is available. Parameters and established before/after facts determine the final class; catalog default is not permission to ignore them.

## Determinism, preconditions, atomicity, and audit

Fingerprint the **complete consumed read set**, not just edited files: logical path/kind/existence/raw-byte hash, directory inventory where discovery matters, normalized Model/IR/semantic digest, effective validation/compatibility policy, selected diagnostic identity, exact recipe version/catalog implementation digest, request and relevant lock/adapter/manifest/evidence pins. A previously absent destination is an explicit absent precondition. Plan identity hashes a versioned canonical projection including ordered operation and expected result digests; no absolute path, clock, hostname, filesystem discovery order or random occurrence token participates.

Revalidate before planning a saved request, after acquiring exclusive custody, immediately before replacing any file, and before finalization. A plan supplied by a user/adapter is decoded and recomputed through trusted registered recipe/#73 operations; compare its entire projected identity and write set, not only its self-claimed digest. Reject missing/deleted/new/renamed files, formatting-only byte changes, changed adapter bundles/policies, target inventory changes and UTF-8 range drift. No force-stale flag. Unrelated concurrent writes to consumed inputs also invalidate the plan; pre-existing unrelated dirty work is preserved rather than requiring or rewriting a clean Git tree.

Conflict planning resolves every recipe against one snapshot, deduplicates exact identical operations, and rejects overlapping incompatible byte ranges or same-member semantic operations, read/write dependencies that change another recipe's precondition, create/delete collisions, contradictory target ownership and path aliases. A batch must not choose a winning edit by traversal order or auto-replan its next recipe. Stable recipe/subject/path ordering determines previews and receipts, not permission to apply conflicting edits.

Proposed transaction state machine: `planned -> prepared -> applying -> validating -> committed`, with failure `-> rolling-back -> rolled-back`; unrecoverable interruption/restoration failure is `recovery-required`. No filesystem offers simultaneous visibility for a multi-file transaction: guarantee no writes on preflight failure, verified restore on ordinary apply/validation failure, and fail-closed readers while an unfinished journal exists. Qualify lock and journal coordination with #73, migrations and generation so one source writer cannot bypass another. Keep journals present continuously through replacements and validation; do not create a reader-admission window while rewriting progress.

Stage and validate candidates in memory/a bounded scratch view before source writes. Back up exact bytes/existence and required metadata, durably write the complete manifest/journal, replace only admitted paths, then load/compile/validate the actual candidate through a transaction-owned read capability. The ordinary public loader must remain blocked by the journal; its bypass is private to this transaction's validator. Check selected findings resolved, no new forbidden diagnostics, actual semantic diff equals prepared diff, compatibility/class does not exceed approval, manifests/ownership and applicable operation obligations hold. A validation failure restores **all** modified files and created/deleted entries, verifies original hashes/existence, records failed validation plus rollback evidence, then releases custody. Receipt finalization is part of commit; never announce success before durable outcome evidence exists.

Some recipes address semantic failures, so a fully accepted before-IR may be unavailable. Retain a bounded syntactically parsed snapshot and original typed diagnostics; set before semantic diff/compatibility to explicit unavailable rather than inventing an empty diff. Such recipes cannot join automatic safe batches until their own preconditions prove equivalence; explicit operations must declare exactly which baseline findings may remain. Syntax/structure/security failure is not blanket permission to write; start the safe vertical slice with fully accepted inputs.

Recovery uses a proposed `.lekalo/cache/fixes/<transactionId>/` local-private home, immutable before-images and exact journal pins, with a shared source-writer gate coordinated with #73. Declare this runtime home in the existing structure/authority/privacy ownership inventory and applicable admitted successors before creating it; do not assume a new cache path grants write/export authority. Preview creates none of it. Store a bounded durable audit receipt for each apply attempt after custody is obtained, including no-op/rollback; read-only/preflight refusals return their audit in the result without creating state. Never overwrite another transaction's backups, clear an unrelated cache, export source-bearing backups, or use Git reset/stash as rollback. Crash recovery restores verified before-images or stays fail-closed when concurrent edits/foreign custody prevent a safe restoration; report the blocker and recovery identity.

Idempotency has two distinct checks: replanning the safe recipe on its result produces no edits; replaying the same bound plan/idempotency key finds its exact committed receipt and verifies current expected after-images before returning unchanged. A matching key with a different request/recipe/input tuple is a conflict. If the source has moved beyond the committed result, return stale/conflict rather than reporting a historical success as current. No-op does not rewrite canonical source, manifest, lock or backups.

Proposed ceilings to qualify: 128 selected recipes, 1,024 operations, 256 touched files, 64 MiB aggregate staged/backup bytes, 16 MiB plan/result and bounded diff hunks. Inherit tighter loader/adapter/diagnostic limits where applicable. Exhaustion rejects before mutation; no silent truncation of a write set, conflict list, validation obligation or receipt. File diff includes exact project-relative paths, create/replace/delete, before/after SHA-256 and bounded textual hunks or binary hash-only view; machine output must not leak raw secret-bearing source. Display redaction does not alter the pinned applied bytes, and changed private bytes can be represented by hashes and withheld hunks.

## Adapter ownership boundary

An adapter-owned ID is `adapter.<adapter-id>.<recipe-name>` with an exact recipe version. Locked manifest/bundle/catalog pins bind which adapter may propose it. Run planning in the accepted read-only confined exchange over declared scopes; reject missing confinement/capability instead of falling back to host execution. Adapter proposals identify staged candidates and typed effects, not arbitrary filesystem writes or shell commands.

Core validates every candidate against manifest lifecycle/owner/generator, scopes, exact before bytes, lock and planned after hashes. No adapter receives a canonical Model write capability. If a target finding calls for a canonical change (e.g. an effect declaration), the proposal may reference only an allowlisted #73 operation type and explicitly selected canonical subject/parameters; core owns and validates that operation in its own transaction. Undeclared extra fields, fabricated owner/ranges, arbitrary pointers, canonical file entries, cross-target namespace claims and scope escalation are denied before writes. A declared operation grants precisely its semantic change, not permission to modify the rest of the containing document.

Regeneration may reuse accepted generate planning for compatible target recipes, but cannot simply call an existing mutating command and claim the outer fix transaction covers it. Integrate prepared candidate files/manifest operations into one host transaction, or expose the recipe as manual-only until that is possible. Artifact plus manifest failure must roll back together. ## Risks and non-goals

- **Dependency contract:** #73 is open and its accepted typed request/transaction seam is absent here. Define the integration first; duplicating text edits or an independent idempotency store would fragment canonical mutation authority.
- **False safe classification:** qualifying an ambiguous name, adding a default/effect, regeneration or removing ownership metadata can change behavior. Require exact proof/class escalation; missing evidence keeps advice manual-only.
- **Rollback placement:** backups and a byte-level transaction do not prove semantic post-validation rollback. Keep the private validation callback, manifest writes and durable receipt within one unfinished journal boundary.
- **Concurrency/crash:** simultaneous visibility across files is impossible; gaps in reader gates, stale directory inventories or independent generation/migration writers can violate all-or-none semantics. Qualify a common writer/reader custody mechanism and failure recovery on every supported OS.
- **Source fidelity:** YAML AST/comment/order handling and Unicode ranges are not arbitrary text-search replacements. Limit initial recipes to formats #73 can preserve, expose unavailable diffs and avoid changing unrelated bytes.
- **Adapter authority:** signed/pinned adapter bytes identify the proposer, not permission for canonical writes. Require confinement, typed operation allowlists and exact target lifecycle/owner checks even for trusted bundles.
- **Version/merge:** 0.6.4 embedded and 0.6.5 successor registries coexist; M8 allocations may land in parallel. Union entries/allowlists and preserve frozen pins rather than repinning all contracts or replacing one branch's registry with another.
- **Privacy/custody:** file diffs and recovery backups may contain confidential source. Use existing classified filesystem/privacy rules, withheld hunks and local-private transaction storage; redaction is not export authorization.
- **Bounded automation:** this issue implements formal registered recipes, not free-form AI patch generation, arbitrary shell/plugin execution, automatic diagnostic repair, interactive first-candidate resolution or general refactoring.
- **Delivery scope:** no external workflow-provider automatic apply, MCP implementation, HLV/AIFHub writes, task scheduling, Git reset/stash/commit by the fix command, baseline/lock update, schema migration guessing, unrelated source cleanup, production deployment or model-quality claim is included. The authorized research commit is separate from any future fix-command mutation.
