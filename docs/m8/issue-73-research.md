# Issue #73: semantic Change API research

Research only, 2026-10-06. Acceptance authority: [issue #73](https://github.com/ichinya/lekalo/issues/73), read live with `gh issue view 73 --repo ichinya/lekalo --json title,body,labels`. Parent [#1](https://github.com/ichinya/lekalo/issues/1) and dependencies [#6](https://github.com/ichinya/lekalo/issues/6), [#8](https://github.com/ichinya/lekalo/issues/8), [#12](https://github.com/ichinya/lekalo/issues/12), [#18](https://github.com/ichinya/lekalo/issues/18), [#21](https://github.com/ichinya/lekalo/issues/21) were read for context only. Source baseline: `15bd13917654dc20ad19b089a5bb8e5e29c2099f`, branch `ichinya/m8-issue-73`, fresh M8 checkout. Checked-in product remains `0.6.5`; the dispatched implementation target is **0.8.0**. This document follows the evidence/inventory, proposal, diagnostic, fixture, acceptance and risk structure of `docs/m7/issue-{77,90,103}-research.md`.

Decision: propose a target-independent `lekalo_core::change` service with a closed typed operation catalog, pure preparation, semantic validation and diff, a lossless source-edit planner, and a separately invoked transaction writer. CLI sugar and a future MCP tool consume the same request and receipt types. Every successful mutation is tied to exact input bytes, policy, idempotency and an audit record; generated outputs are planned separately and written only by an explicit generation request.

All new paths, APIs, contract identities, fields, flags, diagnostic allocations and gates below are **proposals**, not existing behavior or reserved codes. The live issue has ten P1 operation bullets, ten requirements and seven unchecked acceptance criteria; a first add-field implementation is an increment, not completion. This phase changes only this research document and delivers a local commit; it does not implement operations, change contracts or run mutation experiments.

## Proposed command and contract surface

### Commands and flag semantics

The following are exact **proposed** CLI forms. Global `--json` continues to select a machine-readable domain envelope; `--project` is explicit for repeatable examples. Mutation requires `--apply` and `--idempotency-key`; an operation without `--apply` prepares a read-only preview. `--dry-run` is an explicit synonym for preview and conflicts with `--apply`. Preview never reserves an idempotency key or writes caches, locks, audit files or reports.

```sh
lekalo change entity-field:add --project sample --entity tasks.task --name priority --type task.priority --default normal --dry-run --json
lekalo change entity-field:add --project sample --entity tasks.task --name priority --type task.priority --default normal --apply --idempotency-key task-priority-v1 --json
lekalo change command-effect:add --project sample --command tasks.complete --emit tasks.event.completed --dry-run --json
lekalo change request --project sample --request change-request.json --dry-run --json
lekalo change request --project sample --request change-request.json --apply --idempotency-key batch-v1 --expect-plan sha256:<64hex> --json
lekalo change receipt --project sample --idempotency-key batch-v1 --json
lekalo change recover --project sample --transaction <transaction-id> --json
```

The issue's IDs are illustrative, not guaranteed current fixture symbols. `task.priority` belongs to semantic module `task`, distinct from `tasks`; a synthetic example must declare that module/import or refuse unresolved type. `--default normal` is a string/enum literal; `--default-json <JSON-literal>` accepts typed JSON values and conflicts with `--default`. Missing default and explicit null are distinct. No implicit conversion of an invalid enum/default value. JSON request is the complete operation surface; sugar flags lower to the same DTO without guessed names or arbitrary JSON Pointers.

Common proposed flags: `--policy <json-file>`, `--allow-breaking`, `--expect-model sha256:<64hex>`, `--expect-plan sha256:<64hex>`, `--dry-run`, `--apply`, `--idempotency-key <bounded-token>`, `--json`. Policy may authorize an otherwise valid breaking operation; `--allow-breaking` records explicit acceptance of reported compatibility classes and cannot override malformed requests, invalid Models, unsafe paths, incomplete required evidence, ownership denial or stale preconditions. Data-loss/storage consequences need a reviewed policy rule and migration evidence; the boolean flag alone is insufficient. No `--force` bypass.

Default behavior computes an impact and generation **plan** without invoking adapters that mutate files. Explicit subsequent `lekalo generate --project sample --locked` uses the accepted generation service. Proposed optional `change --generate --target <id>` is a separate post-commit orchestration action with its own receipt/status; generation failure must report `model committed, generation failed` and cannot claim all-or-nothing Model-plus-target atomicity. Omit that convenience flag in the first increment; the separate generation command already supplies explicit authorization.

## Proposed preparation, conflict, atomicity and idempotency semantics

1. Decode bounded request/catalog/policy; select one validated project root and acquire a coherent read snapshot. Resolve typed identities/kinds/members and reject duplicate/ambiguous targets. Pin the complete input set, including non-mutated imports, attachments, relevant lock/ownership/policy and canonical history; adding an input file must invalidate the snapshot too.
2. Build one candidate Model and attachment set using typed operations. Preserve semantic IDs for file-only moves, add explicit symbol history/tombstones for identity moves/removals, update known typed field/reference sites and definition versions, and reject unhandled affected reference families. Record field-renames in Change history because fields have no existing standalone symbol IDs.
3. Recompile and validate candidate across project boundaries. Compute semantic diff and compatibility with existing owners plus default/signature extensions. Invalid candidate always refuses; valid breaking candidate requires allowed policy or applicable explicit acknowledgement. Unknown/incomplete required analysis cannot authorize apply.
4. Produce byte edits from exact semantic-owner -> syntax-node associations. Preserve all bytes outside declared edit ranges, including comments, key order, quoting, blank lines, indentation, CRLF and unrelated definitions in the same file. Reparse prospective bytes and assert compiled candidate equality. Removal/move transfers or preserves attached comments by a documented rule; ambiguous ownership or unsupported layout refuses with a preservation diagnostic. Never fall back to whole-project reserialization. Provide both semantic and exact file diffs in preview, with explicit bounded-output refusal instead of a truncated plan presented as complete.
5. Compute impact against base and candidate, using diff/member seeds; join evidence only at matching revision pins. Extract read-only generation-plan preparation with ownership/lock/drift checks. Classify unavailable adapters/attachments explicitly; default plan can be partial, but policy-required gaps deny apply. Produce a deterministic plan digest excluding wall clock, process IDs, absolute paths and replay presentation fields.
6. Apply only a service-created sealed plan. Under a project-wide writer lock, check idempotency ledger first, then revalidate root identity, paths/input inventory, all before digests and expected plan. Same key plus same normalized request/execution intent returns the original committed receipt without another mutation even though the Model now has the field. Same key with another request/policy/intent is a conflict. Optional expected preconditions remain part of intent; preview and apply are distinct modes, not distinct semantic operations. A new key after an equivalent edit may produce a documented no-op; it never invents prior ownership.
7. Stage bounded prospective files/history, immutable verified backups and a durable journal before replacing any source. Journal includes creations, deletions and directory moves, not merely file-content replacements. Serialize mutation across change/migrate/generate/adoption writers; integrate recovery barriers into every Model reader and relevant writer. Revalidate after staging and immediately before replacements to prevent concurrent edits from being overwritten.
8. Apply same-filesystem replacements, verify all after digests, finalize canonical history/idempotency in the same transaction and publish the commit marker. Ordinary failure restores all originals and reports invalid/denied as appropriate; crash leaves a recoverable journal and readers refuse until explicit `change recover`. No success receipt before the commit point. Retain recovery material until finalization is durably established. A committed transaction whose stdout write fails remains discoverable by key; retry must not duplicate it.

The **proposed observable atomicity contract** is one complete Model/history revision or no accepted revision: no preflight mutation, complete restoration on recoverable failures, and blocked reads while an interrupted transaction is unresolved. A power failure can leave physical files partially replaced; the durable reader barrier/recovery prevents treating them as a valid project. This uses the existing migration safety model but requires cross-service integration and fault injection. If unconditional instantaneous multi-file filesystem atomicity is required, a versioned snapshot-root publication design is additional work; do not claim per-file rename satisfies that stronger interpretation.

Receipts distinguish `prepared`, `committed`, `replayed`, `no-op`, `rejected`, `rolled-back`, `recovery-required`. These are Change receipt states, not new `DomainResult::Status` members. Preserve the original diagnostics and full denied plan where safely available. Receipt lookup/replay remains usable after source drift and reports the original committed provenance plus current-state mismatch; it must not reapply or relabel an old operation as a current validation success.

## Diagnostics and registry implications

Allocate codes only after rechecking the implementing M8 union; preserve all prior producers and registry-version selection. ## Risks and non-goals

- **Representation gaps:** defaults and pure emission are real contract work; existing query/error attachments already cover part of the signature surface. Existing adapters must support or explicitly refuse new versions/semantics; a successful CLI cannot silently drop a default or pretend an event is a write effect.
- **Lossless editing:** source spans alone do not preserve comment ownership. Candidate semantic equality, stable byte ranges and refusal cases are required; no canonical formatter or whole-file rewrite as an implicit fallback.
- **Atomicity and concurrency:** create/delete/move and canonical history expand the existing migration writer's guarantee. Without shared lock/recovery barriers, another reader or writer can observe or overwrite a partial revision. Qualify OS/filesystem guarantees honestly.
- **Idempotency custody:** a disposable cache is insufficient durable replay evidence. Include history finalization in the commit; key reuse conflicts, corrupted history and stdout failures require separate outcomes. Idempotency is project-scoped, not a distributed exactly-once service claim.
- **Identity/history:** physical moves differ from semantic renames; field history differs from symbol history. Rewriting only core refs leaves attachments/bindings/trace stale. Reject unresolved affected families instead of publishing an incomplete successful migration.
- **Policy interpretation:** the issue's invalid/breaking wording cannot authorize invalid Models. Compatibility acceptance is scoped and audited; safety, validation, ownership and required-evidence failures stay non-bypassable.
- **Impact/generation evidence:** relevant planning does not execute gates or establish runtime equivalence. Removed nodes need the base graph; stale manifests and missing observed/native evidence are not zero impact.
- **Shared M8 contracts:** diagnostic union, product version, Model/IR/diff, adapter/version registry, structure and authority admission are integration seams. Reinspect the actual implementing base and freeze unaffected families; independently green increments do not prove merged CI acceptance.
- **Privacy:** requests/file diffs/audit history can expose domain names/defaults/source. Keep local by default, use approved classification/export paths and avoid environment/absolute-path/secret payloads. Do not write external requirements, HLV, AI Workspace or AIFHub stores through this API.

Non-goals: arbitrary textual patching or executable user migration scripts; target-language refactors; silent inferred mapping promotion; implicit formatting/generation/lock refresh; destructive orphan cleanup; semantic module-ID renaming without a separate ID-contract change; distributed transactions across target/external systems; publishing a MCP server; measured AI productivity claims. These do not remove any of the issue's listed P1 operations or acceptance criteria.
