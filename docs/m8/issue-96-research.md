## Proposed command/report schema and artifacts

### Exact CLI grammar and status behavior

```text
lekalo explain CODE [--registry-version VERSION] [--locale en|ru] [--adapter-explanations FILE] [--recipe-catalog FILE] [--json]
lekalo explain --diagnostic-file FILE [--locale en|ru] [--adapter-explanations FILE] [--recipe-catalog FILE] [--json]
lekalo explain LEK-TYPE-014
lekalo explain LEK-HIDDEN-009 --json
lekalo explain --diagnostic-file report.json
lekalo --json explain LEK-HIDDEN-009
```

CODE and `--diagnostic-file` are exactly-one selectors. VERSION accepts an exact admitted registry version, never a SemVer range; code lookup defaults to the current producer registry and permits explicit lookup in another bundled admitted snapshot. File input selects each item's own registry_version; disallow `--registry-version` with file mode. The three issue commands are supported grammar, but the unregistered `LEK-TYPE-014` intentionally demonstrates a distinct unknown-code result until its own rule owner publishes it. CODE is case-sensitive, grammar checked, and never autocorrected to a similar registered code. Dotted IDs are output identity, not an undocumented CODE alias.

`--locale` controls human projection only, defaults to `en`, and supports explicit `ru`; ambient OS locale cannot alter either projection. JSON bytes are identical for en/ru, including canonical English prose, code, fields, alternatives and examples. An unsupported locale is an explicit unsupported result; missing required locale keys are catalog errors, not silent partial translations. Existing global `--json` works before or after the subcommand. Help documents that advice is generic and imported context has not been checked against live source.

File mode admits (1) one diagnostic item v0.2.16, (2) an exact supported diagnostic-bearing DomainResult envelope, or (3) CI report v0.6.3. Reject unknown shapes, unknown wire versions, unknown/duplicate keys, inconsistent id/code/message_id/category, invalid severity/profile joins, bad paths/spans and registry-invalid data. Maintain an explicit envelope-shape allowlist verified against current producers, not an arbitrary object-with-diagnostics heuristic. Do not import SARIF/JUnit/free text/SQLite or walk arbitrary nested objects. A recognized empty report produces valid/0 with empty explanation/occurrence arrays; it says no imported diagnostics, not that project validation passed. Never inherit the original operation's failing exit as the explain lookup exit.

Proposed limits: 8 MiB per explicitly supplied regular file, depth 32, 256 occurrences, 2 MiB rendered report, and bounded per-field/entry content enforced by schema and runtime. Over-limit input refuses rather than truncating. Reuse safe logical diagnostic paths and classified reads; reject linked/nonregular inputs, avoid emitting OS paths/errors, and never discover files recursively. The file selector is an explicit local path; it is not copied to output. Imported messages must match approved registry text or be withheld, and arbitrary envelope extras cannot escape into context. Successful imports preserve approved structured data, safe spans, causes, fix IDs and metadata separately.

Lookup succeeds valid/0 even if an imported occurrence is error severity. Unknown well-formed CODE is unsupported/4 with `explain.code-unknown`; a known registered code missing documentation is invalid/1 with `explain.catalog-invalid`, never unknown. Unsupported registry/schema versions are unsupported-version/5. Malformed invocation remains `cli.usage` under existing parser behavior. Failed local reads are unavailable/4; malformed imported bytes are invalid/1. Multi-diagnostic input is preflighted completely; any failed lookup refuses the batch, with bounded sorted problem diagnostics rather than a deceptively complete partial report.

### Entry and response semantics

Proposed catalog root: `{schemaVersion, identity, owner, registryRefs, entries}`. `owner` is a closed core-or-adapter union; adapter owner includes its exact ID/version/artifact digest and provider namespace. Registry references include version/digest and binding coverage. One entry contains:

- `ruleId`, `code`, `semanticsRevision`, `registryVersions`, `lifecycle`, `title`, `category` and `textKeys`;
- `checks` (predicate, required evidence, applicability and known limits), `importance` (correctness/portability/AI-readability rationale) and `commonCauses` with stable cause IDs;
- `alternatives` with stable alternative ID, `kind: safe|unsafe|breaking|manual-only`, preconditions, consequences, manual instructions and an explicit recipe-reference state;
- `examples` with stable example ID, before/after snippets, trigger/non-trigger fixture refs, expected code/outcome and claim limits; snippets are inert text, not executable commands;
- `relatedRules` as exact registry/rule/revision refs, `profileBehavior`, `targetNotes`, `documentationRefs`, and `waiverPolicy`;
- for adapter-owned entries, `providerExplanationRef` containing namespace, originalCode, immutable provider explanation ID/version/resource digest and original versioned documentation link.

Proposed successful report root: `{schemaVersion, identity, status, catalogRefs, explanations, occurrences}` with status `valid`. `explanations` contains the validated canonical entries, sorted by registry version/rule ID/revision/owner; occurrence records reference this tuple and carry approved original diagnostic context. Keep original imported order index while sorting output deterministically. Occurrences include registryVersion, diagnostic identity, reported severity, safe symbol/source/data, causes, original suggested-fix IDs and provider metadata; any available imported profile/provenance has an explicit verified-imported or unknown state. They assert `sourceApplicability: unverified` and never claim current source or fresh fingerprints. Generic causes are not inserted into the occurrence's actual causal chain.

Versioned documentation links include a release-tag/commit pin and exact rule anchor; the corresponding bundled resource is available offline. Never use mutable latest pages as rule-semantics authority. Links are display metadata, never automatically opened or fetched. Catalog coverage includes registered reserved/retired entries with explicit lifecycle/limitations and replacement refs, without implying that such rules execute.

## Proposed fixes, profiles, waiver and adapter boundaries

**Fix join:** alternative kind describes the risk of the generic operation, not proof its preconditions hold here. Recipe state is `available` (exact recipe ID/version/owner/digest, manifest schema ref and declared applicability), `unavailable` (registered fix ID plus reason), or `manual-only` (no executable handle). A safe recipe reference must match the owning rule's allowed_fix_ids and #74 recipe manifest; stale version/digest, foreign owner, missing recipe or mismatched applicability refuses the join. Until #74 publishes valid fix IDs and recipes, existing alternatives stay manual instructions with explicit unavailable execution. Listing a safe operation is neither permission to mutate nor a completed fingerprint check.

When #74 is implemented, it alone evaluates current source fingerprints, scopes, atomic edits, post-validation, rollback and audit receipts. #96 does not duplicate its execution engine or expose `--apply`, `--safe`, automatic shell snippets, or implied dry-run guarantees. Unsafe alternatives require human review; breaking alternatives carry visible **BREAKING** labels in human output and `kind: breaking` plus compatibility consequences in JSON. Manual-only alternatives are equally explicit. Adapter-owned recipes cannot be advertised as core Model mutation authority.

**Profiles and waivers:** explain default and allowed effective severities from the registry and admitted profile documents, plus #84's coverage/obligations and policy denial behavior. Catalog rationale must preserve differences between semantic correctness, measured thresholds and advisory style. Include explicit limitations when a profile requires missing native evidence. Waiver policy is `forbidden`, `owner-scoped`, or `not-applicable`, with exact owner/schema refs, applicable condition/scope/expiry requirements and retained audit/raw-finding behavior. Security/mandatory semantic failures cannot acquire a waiver by appearing in an explanation. A generic policy note is not a decision that a particular occurrence is waived.

**Provider join:** `--adapter-explanations FILE` admits one bounded catalog with an exact adapter owner and immutable original explanation reference. Match the imported metadata's versioned provider namespace and original_code; never derive provider code from the mapped LEK code alone. Different providers may map to the same core rule but keep separate explanation tuples and original references. A provider cannot replace core meaning or reuse core IDs as provider ownership. Conflicts or invalid owner/digest joins refuse. A missing optional local provider catalog retains namespace/originalCode with `providerExplanation: unavailable`, preserving any admitted reference and making no fabricated text claim; adapter acceptance requires the real reference to be present and resolved.

Ship reference text/resources with the adapter catalog for offline operation. No runtime adapter launch, installation or protocol negotiation occurs. Existing provider diagnostic wire has no explanation-reference member, so add references solely in the independently versioned catalog/report. If a future adapter requires transported references, that is a separately owned protocol successor, not an implicit #96 edit to the frozen protocol.
