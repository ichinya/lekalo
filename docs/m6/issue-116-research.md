## 3. External evidence and supported-version decision

Context7 was resolved first for Drizzle ORM and queried using `/drizzle-team/drizzle-orm-docs` (official repository, high reputation). These are documentation observations, not a tested compatibility claim:

- PostgreSQL uses `pgTable`, generated identity/serial, enums and PostgreSQL index syntax; MySQL uses `mysqlTable`, autoincrement and its own type constructors. [PG schema declarations](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/sql-schema-declaration.mdx), [MySQL overview](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/mysql/overview.mdx).
- Application-level relations can exist without database foreign keys. Current docs include `defineRelations` with `from`/`to`; older `relations` with `fields`/`references` needs a separately pinned compatibility row. `one`/`many` alone cannot prove enforcement, required participation or every neutral relation field. [Relations](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/relations.mdx).
- MySQL `$returningId()` describes inserted keys, not a PostgreSQL arbitrary `.returning()` projection. Upsert `onConflictDoUpdate` has explicit target/set structure. [Returning IDs](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/latest-releases/drizzle-orm-v0320.mdx), [Upsert](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/guides/upsert.mdx).
- Transaction callbacks/config and nested boundaries are syntax evidence; PostgreSQL isolation/access/deferrable options belong in target evidence. Runtime hooks such as `$onUpdate` are not migration defaults. [Transactions](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/transactions.mdx), [MySQL column hooks](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/mysql/column-types.mdx).
- Drizzle migration layouts vary by Kit generation: current docs show migration folders with `snapshot.json`/`migration.sql`, and v1 changes remove the journal. Recognize only an explicitly pinned layout, without executing Kit/config/migrator. [PG migrations](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/pg/migrations.mdx), [v0/v1 layout changes](https://github.com/drizzle-team/drizzle-orm-docs/blob/main/src/content/docs/sqlite/v0-v1-changes.mdx).

S1 must capture an exact supported ORM/Kit release, upstream declaration archive integrity/license and APIs for each fixture row; no `latest`, semver-range-only, or guessed beta support. Start with one qualified released API generation in both PostgreSQL and MySQL; add a second relations/layout generation only with its own pins/tests. An unqualified consumer version yields explicit unsupported/unknown evidence. The private pilot is subsequent adoption evidence, not a prerequisite for these synthetic offline fixtures.

## 4. Evidence, provenance, completeness and confidence model

### 4.1 Proposed target evidence contract and storage

Add `contracts/drizzle-evidence.schema.v0.4.0.json`, implemented by new `adapters/node-typescript/src/drizzle-contract.mjs` and `core/drizzle_evidence/{mod,wire,validate,bindings,effects,store}.rs`. This is a closed target attachment, not a new Model definition. Separate arrays: tables/columns/defaults, constraints/indexes, relations/join tables, queries, transactions, migration references, scope predicates, test references, binding candidates, limitations and source locations. Every reference resolves or carries an explicit unresolved state.

Required envelope data: schema identity/version; project/target/profile; adapter version and launched artifact digest; compiler version/options digest; ORM/Kit version and declaration-bundle digest; extractor/rule-set version; input manifest/revision; Model/IR/projection pins when comparing a contract; class/provenance and exact `policyRef`/`authorityRef`; `readOnly: true`; per-section completeness with reason tokens. DB-state evidence is `unknown` unless a separately supplied, validated introspection/runtime document proves it. No credentials or connection fields are necessary for static evidence.

Each fact carries native identity, rule ID, occurrence, source file content digest, signature/semantic-shape digest, dependency-input digests, confidence and freshness. Locations are normalized project-relative paths plus start/end line and column (1-based, TypeScript UTF-16 column convention), with repository-role alias; retain distinct spans for relation callback, constraint, query mutation and transaction callback. Location maps live in evidence, never copied into storage declaration or core IR. Dialect properties and unsupported expressions are bounded target tokens/digests, not executable SQL or source excerpts.

Core host persists validated evidence under proposed `.lekalo/import/drizzle/<evidence-digest>.json` with a current digest reference; the authority kind is existing `lekalo.observed-model-draft`, whose accepted home is `.lekalo/import/**`. The adapter writes no files. Persist only when the exact privacy decision permits that repository destination; `local-private` remains in the existing local runtime store, excluded from repository tracking. Use `core/privacy/{evaluate,export,context}.rs`, not a local kind/disposition alias. Invalid pin, payload digest, classification, scope or reference refuses before persistence; export/inspect/context apply their destination policy again.

### 4.2 Primary evidence and honest coverage

| Evidence condition | Binding confidence/freshness | Effect trust and consequences |
| --- | --- | --- |
| Checker resolves the symbol/signature to hash-pinned Drizzle declarations; syntax and dependencies are in scope | `exact` for symbol identity; `high` for an extraction rule; current only after input verification | `Current` -> `extracted`; describes static behavior, not a runtime-verified DB mutation. |
| Naming/type-based entity or relation candidate | `medium`/`low`, inferred, full candidate set when ambiguous | `Inferred` -> `inferred`; no canonical subject mapping until owner confirmation; no invented relation/delete policy. |
| Missing declaration, `any`, unresolved alias, raw SQL, dynamic builder, unsupported version/expression or escaped transaction handle | `unknown` or bounded lower confidence; section incomplete | `Unknown`; retain independently proven facts but never convert missing fields/effects into an empty complete set. |
| Source/query/schema/config/lock/declaration/rule/projection pin changed or disappeared | `stale` (freshness is separate from confidence) | `Stale` -> `unknown`; stale joins remain visible, cannot compare as matched or satisfy verification. |
| Owner confirms one candidate | Mapping becomes user-confirmed; scan origin/revision retained | Confirmation establishes identity mapping only; extracted effects remain extracted, and schema enforcement/runtime still unknown. |

Observed confidence (`exact/high/medium/low/unknown`) differs from effect confidence (`canonical/verified/extracted/inferred/unknown`); map them deliberately, not by copying tokens. `Verified` is reserved for accepted verification evidence, not successful parsing. Register an explicit mapping between the flat protocol adapter ID `lekalo-target-node-typescript` and the namespaced identities required by `EvidenceEnvelope`; do not pass the flat ID into that grammar or normalize it ad hoc.

Freshness key includes **all** enumerated input bytes: query bodies as well as signatures, imported tables/relations, tsconfigs and references, manifest/lock, schema/config/snapshot/migration references, trusted declaration and extractor pins, projection and binding revisions. A changed table invalidates dependent queries/relations/effects; an implementation-body change with unchanged TypeScript type still invalidates query evidence. Recheck byte digests when loading/attaching, not only during scan. Missing dependencies stay unknown. Whitespace can change source revision without implying a semantic change; never reuse the previous byte-current receipt blindly.

Rename handling: invalidate old bindings by default. Rebind a Model rename only through accepted semantic history; rebind physical table/column names only through `StorageRenameMap` validated against exact old/new attachments plus a rescanned new native symbol. Projection history alone cannot prove a TypeScript property rename; require a reviewed native mapping as well. Duplicate/cyclic/ambiguous history, missing target or wrong digest refuses. No nearest-name matching.

## 6. Executable implementation sequence

### S1 — Contract, release pins and protocol design (first implementation commit)

1. Record decisions in new `docs/drizzle-bindings.md` and an allocated ADR `docs/adr/<allocated>-drizzle-evidence-bindings.md`: static vs DB evidence, target-side declarations, evidence transport, confidence/freshness, privacy authority and dialect/version support matrix. Produce new `adapters/node-typescript/drizzle-toolchain.lock.json` with exact release/declaration digests and API/layout support rows; update notices when vendoring declarations.
2. Implement the closed schema/decoder from §4, negative vectors and `scripts/test-drizzle-evidence-contracts.mjs` using the existing Ajv convention. Add explicit bounded record/ref/span counts and reject duplicates/dangling refs, malformed digest/path, source text/secret/unknown members. Apply the product-version policy to every changed schema, identity and Rust/JS version table.
3. Add negotiated successor `contracts/target-protocol.schema.v0.4.0.json`: typed Drizzle evidence in scan result, explicit per-section completeness/limitations, no arbitrary JSON or file-path-only reference to inaccessible adapter storage. Mirror in `core/target_protocol/{wire,version,capability,transport,conformance}.rs`, kernel validation/projection and contract tests. Old 0.3.2 clients must receive their old shape or refuse; a new shape cannot masquerade as 0.3.2.
4. Extraction transport success is separate from verification success: a validated incomplete dataset may be retained only by the successor client that honors incompleteness. Old partial-error handling stays fail-closed. Verification with incomplete relevant evidence cannot return pass. Define a no-truncation error/limitation policy; payload caps must never silently erase fields or effects.
5. Register static capability **`scan.drizzle-schema`** instead of reinterpreting `scan.schema`; document this deliberate mapping of the issue's possible operation. Register `scan.queries`, `bind.storage`, `bind.relations`, `detect.effects`, `verify.query-contracts`; keep existing `verify.schema-projection` semantics. Domains are scan/bind/verify, not new dotted operation tokens. Capabilities are partial until the documented subset is qualified. Update kernel, core registry/profile catalogue, manifest and handshake goldens together.

### S2 — Shared compiler context and standalone packaging

1. Refactor `scanner.mjs` to expose a bounded analysis visitor/context (`ts`, checker, Program, inventory and digest inputs) used within one scan; implement new `drizzle-{schema,relations,queries,bindings,effects,migrations,tests}.mjs`. Preserve ordinary scanner results and configured resolution options; no `ts.sys`, ambient module, network or emission fallback.
2. Add `drizzle-declarations.mjs`: build-time embedded upstream `.d.ts` closure for each qualified version, identity/integrity provenance, and type-context-only resolution. Do not execute Drizzle/consumer JS, load arbitrary `node_modules`, or export dependency declarations as project symbols. Unresolved/mismatched consumer pins and forged local lookalikes must degrade rather than acquire Drizzle identity. If the complete declaration closure cannot be safely vendored, return unsupported until an authorized hashed declaration input seam is qualified.
3. Fix manifest-key coverage for other inputs; add schema/query semantic digests and dependency edges. Existing file/byte/depth/request bounds still apply. Lock/config roots must be explicit narrow launch-profile grants; never widen from a request or follow dynamic `drizzle.config.ts` imports.
4. Add `drizzle-extension.mjs` as a helper descriptor and new `scan-composite.mjs` as the **single** registered scan owner; compose ordinary symbols and Drizzle facts deterministically. Compose applicable Drizzle verification into existing `generation-composite.mjs`; use a single bind descriptor if needed, returning proposals only. Source mode lacking a compiler honestly reports unsupported for Drizzle scan.
5. Update `build.mjs` scratch-source copying/embedded declarations/bundle registration, `main.mjs`, compiled `adapter.mjs` and manifest regeneration. Production scan must work with only the committed single-file artifact; `adapter-zod.mjs` need not claim Drizzle support. Regenerate manifest integrity after all artifact/metadata changes.

### S3 — Extraction and contract verification

1. Implement all §5 facts with checker-bound callees and alias/re-export resolution. Static literal folding is bounded and pure; never evaluate default functions, callbacks, config, custom types or SQL. Keep physical storage names/types and dialect notes separate from neutral field IDs.
2. For queries, distinguish builder construction from an observed execution site (`await`/qualified terminal call); unawaited builders describe possible query effects only. Dynamic/conditional/escaped chains and custom wrappers remain incomplete. Insert/upsert may create **or** update, so preserve alternatives/conditions rather than claiming both happened. A typed builder alone is not runtime proof.
3. Compare extracted tables/relations to a supplied, validated `StorageProjectionAttachment` and compiler inputs/projections to bound Query Model/operation contracts. Report matched/missing/divergent/unknown per field/constraint/relation, with missing policies/coverage explicit. Build a correct synthetic projection rather than altering the existing planner declaration to fit a bad schema.
4. Default and relation mapping is representability-first: known neutral literal/now values can compare; arbitrary SQL/client hooks/opclasses/prefix expressions remain target limitations. `one` without unique evidence never becomes a proven one-to-one database constraint. Omitted min/delete/coverage never gets an invented neutral declaration.

### S4 — Host binding, freshness, effect ingestion and privacy

1. Implement `core/drizzle_evidence/` parsing/validation/store and `core/observed/scan_service.rs` ingestion of the negotiated dataset. Keep detailed rows in a referenced sidecar and preserve normal symbol rows; extend observed scan/index successor schemas only for typed references/pins actually required. Bind ownership stays in `observed/bindings.rs`: inferred -> reviewed proposal -> explicit confirmation, all candidate identities retained.
2. Add immutable evidence refs and current pointer to `observed/store.rs` using accepted host ownership, atomic publication and privacy decisions. Recheck every dependency on `bindings audit`, graph load and verify; preserve stale facts for inspect while excluding them from positive verification. ## 7. Open risks and decisions before implementation acceptance

1. **Version drift:** current docs span released/beta relations and Kit layouts. S1's exact compatibility rows are a blocking input for recognizers and declarations; no unpinned docs example is the support matrix.
2. **Protocol/capability scope:** typed successor transport, partial-data consumption and `scan.schema` collision require registry/contract review. Do not avoid this by expanding free-form detail or claiming DB introspection from static declarations.
3. **Declaration closure and artifact size:** real upstream types can require driver/dependency declarations and exceed embedded-library/request/process bounds. Qualify the bounded closure and bundle on the confined runtime; inability to resolve safely is unsupported, not permission to read installed dependencies.
4. **Symbol and body fidelity:** wrappers, overloads, SQL expressions, runtime defaults, dynamically assembled projections and conditional transactions are not exhaustively decidable. Publish the supported subset and residual uncertainty; body/dependency freshness is mandatory even when signatures do not change.
5. **Relation inference:** Drizzle relations do not supply every neutral policy/cardinality/coverage field. Owner-supplied binding declarations are needed; #116 cannot silently create a complete storage attachment, aggregate ownership or tenant enforcement from names.
6. **Existing fixture quality:** #117 MySQL text gate can pass despite missing `tenantId` and mismatched ID storage representation. New compiler/type/physical comparison negatives must reproduce the defects before any coordinated fixture correction.
7. **Consumer integration:** persisting facts does not make them visible; declared-only graph builders and context planning must load/attach the same verified evidence. Incomplete/stale transaction facts must remain visible, with explicit omission when context budget prevents inclusion.
8. **Privacy and pilot:** source-relative spans, physical table names and tenant predicates can still be private. Exact #119/#120 decisions govern persistence/export; public fixtures are synthetic. Private consumer analysis/adoption and real DB/runtime proof need their own authorized work and are not claimed here.
9. **Transaction representation:** the boundary token is not sufficient implementation. AC5 uses validated sidecar boundaries plus attached effect groups, including empty callbacks; a future subjectless-boundary graph change needs its own effect-contract regression gate.
