# Работа с HLV и без него

HLV — дополнительный слой валидации и прослеживаемости требований.
Он фиксирует результаты проверок и позволяет связывать их с требованиями,
реализацией и тестами. Для работы через Lekalo HLV не обязателен.

Сайт HLV: [hlv.cutcode.dev](https://hlv.cutcode.dev).

Lekalo отвечает за семантическую модель приложения, bindings, генерацию
и проверки своих контрактов. HLV добавляет результаты валидации и
traceability по настроенным правилам проекта. Тесты, линтеры и сборка
остаются проверками native toolchain; HLV не заменяет их.

## Сравнение

| Что сравниваем | Без HLV | С HLV |
| --- | --- | --- |
| Модель, генерация, bindings | Работают через Lekalo | Работают так же |
| Тесты, линтеры, сборка | Запускаются напрямую или через CI/native gates | Их результаты могут входить в проверки HLV |
| Подтверждение требований | Связи требований с проверками поддерживаются в документации или trace | HLV формирует результаты валидации и traceability по настроенным правилам |
| Приёмка изменений | Решение по тестам, CI и ревью, с учётом правил проекта | Дополнительно можно требовать прохождения HLV gates |
| Поддержка процесса | Не нужно настраивать HLV | Нужно поддерживать HLV-контракты, связи и проверки |
| `doctor` | Без переданного trace может показывать `degraded` | Корректный trace без gaps устраняет эту причину; само наличие HLV её не устраняет |

## Пример: запрет редактирования чужой задачи

В приложении добавляется требование: «пользователь не может редактировать
чужую задачу».

Без HLV разработчик реализует правило, добавляет тест и запускает проверки.
Связь теста с требованием поддерживается в документации или trace manifest.
Приёмка опирается на результаты проверок и ревью.

С HLV требование дополнительно связывается с соответствующей проверкой,
а её результат входит в HLV gate. При приёмке можно проверить, что
доказательство относится к нужной версии изменения. Это требует настройки
связей и проверок: HLV не создаёт покрытие автоматически.

## Trace можно использовать без HLV

Нейтральный [trace manifest](trace-manifest.md) описывает цепочку:

```text
требование → символ модели → binding/код → сценарий/тест → HLV или native gate evidence
```

Он помогает видеть, чем подтверждено требование, где отсутствует покрытие
и к какой версии относятся доказательства. Результатом в конце цепочки
может быть native gate; присутствие HLV не является условием использования
trace. HLV владеет своими результатами валидации и диагностики, а требования
и модель сохраняют владельцев, указанных в [authority matrix](authority.md).

## Почему `doctor` показывает `degraded`

В текущей реализации проверка `integrations.hlv` необязательна для всех фаз
readiness, включая `verify` и `release`. Несмотря на название, она проверяет
trace manifests, переданные через `--trace`, а не наличие установленного HLV.

- Trace не передан: `degraded`, причина `not-supplied`.
- Переданный trace содержит gaps: `degraded`, причина `trace-gaps`.
- Переданный trace не проходит валидацию: проверка `blocked`, причина
  `invalid-manifest`; такой вход нельзя считать корректным доказательством.
- Все переданные manifests проходят валидацию и не содержат gaps:
  проверка `ok`, причина `evidence-current`. Это статус данной проверки,
  а не подтверждение выполнения всех требований приложения.

Если единственная причина `degraded` — отсутствие необязательного trace,
а обязательные проверки зелёные, работу через Lekalo можно продолжать.
`doctor` сообщает о неполноте сведений; он не запускает HLV gates или тесты
и не заменяет приёмку. Подробнее: [doctor и readiness](doctor.md).

## Когда HLV нужен

HLV полезен, когда проекту нужна систематическая приёмка по требованиям:
явные связи с проверками, результаты gates и доказательства для конкретной
версии изменения. Он становится обязательным только по отдельному правилу
workflow проекта, например если приёмка требует определённого HLV gate.

Само подключение HLV не гарантирует полноту проверки. Качество результата
зависит от настроенных правил, покрытия тестами и актуальности доказательств.
