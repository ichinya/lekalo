## 1. Existing generation seam and exact semantic inventory

`contracts/model.schema.v0.2.16.json` is the accepted source Model schema, not a schema for arbitrary execution instructions. Compiled IR is `dev.lekalo.ir@0.2.16`, implemented by `crates/lekalo-core/src/ir/mod.rs` and serialized in `ir/canonical.rs`. There is no `operation` or `operation.step` definition kind in this schema/IR. Do not add either through permissive PHP decoding. The actual inputs are:

- `CommandDef`: `id`, common metadata, `input: Vec<Field>`, `effects: Vec<SymbolId>`. There is no command output, ordered business body, transaction or actor field. An effect list is not a sequence of executable assignments.
- `QueryDef`: `reads: Vec<SymbolId>`, optional `returns: TypeRef`; there is no query input field. Parameters, filters and pagination belong to the separate `query-model.schema.v0.2.16.json` attachment and `src/query_model/`.
- `PolicyDef`: `applies_to` plus closed `decision=allow|deny`. This is insufficient to invent owner/tenant predicates. `authorization.schema.v0.2.16.json` and `src/authorization/{document,evaluate,parse}.rs` own actors, scopes, bindings, predicates, composition and mapping completeness. `decision=deny` does not mean “deny only if the actor name contains bulk”.
- `EffectDef`: `operation=create|update|delete`, entity reference and emitted event IDs. `effects/build.rs` projects query reads, command CRUD and effect emissions, validating referenced kinds; it does not infer fields, payload expressions, repository methods or execution order. `effects::OperationId` uses `operation:<semantic-id>`; that reference vocabulary does not create an IR operation node.
- `transaction-concurrency.schema.v0.2.16.json` and `src/transaction_concurrency/{effect_group,operation,precondition,isolation,lock}.rs` provide `OperationContract`: operation/version, required/optional/forbidden transaction, atomic groups, isolation, preconditions, failure boundaries, idempotency, retry and capabilities. These are separate declarations, not runtime enforcement.
- `extended-effects.schema.v0.2.16.json` and `src/extended_effects/` own event/job/external/cache/publication contracts, delivery and capability references. Reuse these for dispatch ports; do not reinterpret every CRUD effect as a queue job.
- `error-contract.schema.v0.2.16.json`, the error registry and `src/error_contract/` own output/error unions and retry semantics. A command unit success is distinct from null query output. HTTP serialization belongs to `transport-http.schema.v0.4.0.json`; client SDK projection is a consumer, not authority for server behavior.
- `scenario-map.php::{php_operation_index,php_resolve_operation}` indexes commands/queries and resolves scenario kind-qualified references. Scenario `when` steps describe test actions, not handler implementation steps. Preserve this distinction in manifests and diagnostics.

The inspected `contracts/*.v0.4.0.json` families already cover types input/map/evidence, contracted declarations, scenario runs/test ports, storage/migrations, transport/client SDK, classification/data flow, NFR and validation profiles/diagnostics. None defines a PHP handler execution plan or complete observed method contract. Reuse their owning semantics by validated reference instead of copying unrelated fields into Model.

Existing adapter dispatch is exclusive: `kernel.php::deterministic_generation` selects scenario generation, then `resolve_types_request`, then kernel/migration generation. Core `orchestration/generate.rs::generate` stages `.lekalo/cache/ir/<project>.json` and passes that evidence path to the adapter. #58 finds `lekalo/types/<project>.types.json` from it. Adding a suffix branch alone would repeat #58's original pipeline bug; putting operations before types would silently suppress type generation.

**Proposed composition:** resolve all explicitly selected families from the canonical project evidence; map and validate their dependencies before combining deterministic file plans. Generate missing managed types and operations in one authorized plan, or verify an explicitly bound existing type map. Reject overlapping paths/FQNs and any failed required family before publication. Keep explicit scenario/migration inputs working; preserve ownership entries for families not selected by a run. Apply the same applicability and input resolution in generate, validate and verify.

## 2. Proposed PHP constructs, signatures and supported semantics

Baseline remains PHP 8.3 with `declare(strict_types=1)`. Portable application classes use constructor-injected typed dependencies and one public business entrypoint, `handle`; constructors and private helpers do not count as extra operation entrypoints. No controller/model/observer body contains the use-case algorithm; Laravel adapters sit outside the portable namespace. Do not generate a service locator, a hidden dynamic command bus or untyped arrays as public handler signatures.

Reuse #58's implemented `type-policy.php`, `type-map.php::php_map_types`, `type-emit.php::php_emit_types` and `type-codec.php`. Their maps identify nominal scalar/enum/VO/entity/command/event types, codecs and presence wrappers. Resolve the exact type-map entry and digest, not an assumed FQN from an operation name. Preserve required versus nullable independently, exact wire spelling and nominal IDs. Query map FQNs currently identify a `ResultCodec`, not a result DTO: derive the handler return type from `returns`, never return the codec class.

**Proposed role inventory:** command input from #58; operation-specific result/error variants from the validated error binding; query input from query-model (an explicit empty input if the verified parameter set is empty), result from IR/query contract; `ActorContext` and policy port from authorization; narrow read/write repository interfaces; typed transaction, clock/ID, event and job ports when declared. A proposed `FocusTaskHandler::handle(FocusTaskInput $input, ActorContext $actor): FocusTaskResult` illustrates the shape only. The actual result payload must come from the error/output contract, not this example or an HTTP controller response.

#58's current input accepts only project/IR/policy and its mapped kinds have no error/result-union role; its emitter does not yet consume error-registry or query-model attachments. Implement those missing operation roles under the new operations family, reusing type mapping/codec primitives, rather than claiming they already exist or silently adding fields to published php-types v0.4.0. If sharing requires a type-contract change, version that family and update all consumers together. Undeclared errors and infrastructure exceptions stay distinct from the domain union; boundary serialization exposes only declared public payloads.

**Proposed managed subset:** a closed, versioned recipe vocabulary in the target operations input, initially an explicit typed port delegation and a bounded single-entity update recipe. Each recipe names its read/key bindings, assignment expressions, preconditions, policy, transaction group, declared errors and dispatch bindings. Operands are typed input/actor/clock/literal or validated expression references; no PHP, SQL, eval, arbitrary callbacks or loops. Require exact type/effect/authorization reconciliation. A single update recipe must name all assignments and missing-record behavior; an `update` effect alone authorizes none of them. Unsupported expression, multiple-store atomicity, arbitrary branching, recursion or compensation workflow refuses managed generation with a bounded reason.

This recipe is new target metadata, not a fictional pre-existing `operation.step` IR. Record the decision in an ADR. Longer-term portable executable operation semantics need their own reviewed neutral contract; #59 must not introduce a general workflow language accidentally. Managed wrappers may call a maintained body, but the manifest must label that body custom/scaffolded, never claim that the business algorithm was generated.

Planner needs a coherent acceptance corpus before code generation. `ir-minimal.json` declares `planner.create_task` as create while the fixture controller updates an existing row; `planner.focus_task.effects` also directly names an event, whereas `effects/build.rs` requires Effect definitions. Its `count_focused` returns `planner.task_state`, not a numeric count. Runtime fixtures use `task-1` although the type corpus declares a UUID. Preserve old regression inputs as historical tests; create a reviewed source Model plus attachments that compiles and validates together, derive its IR, and use valid UUIDs. Do not patch evidence digests or infer corrected semantics from names.

## 3. Contract, roots and custody decisions

**Proposed new closed families**, with versions allocated at implementation landing under `docs/versioning.md` (not automatically v0.4.0): `php-operations-input.schema.v<release>.json`, `php-operations-map.schema.v<release>.json`, `php-operations-evidence.schema.v<release>.json`. Reuse the generic ownership manifest, contracted declaration and canonical effect graph rather than inventing competing ownership or effect identities. No change to Model/IR is required by the initial projection.

Input top-level shape: schema/identity, projectId, exact IR evidence digest, references with digests to type map, error/query/authorization/transaction/extended-effect inputs as required, target/profile binding, and operation records. Each record names semantic ID/kind, implementation mode, signature roles, explicit native binding, dependencies, policy/scope mapping, transaction binding and recipe or maintained body reference. Laravel container metadata declares interface-to-implementation, constructor slot, lifetime and connection/scope tokens. Missing required context is a finding; absence is never “public”, “no transaction” or “pure query”. Reject duplicate operation/port bindings and ambiguous contextual bindings.

Canonical homes proposed:

- Author input: `lekalo/operations/<project>.operations.json`, mirroring types; only bounded, flat matching files admitted by `project_fs.rs`, no arbitrary sibling discovery.
- Core-derived joined evidence: `.lekalo/cache/php-operations/<project>.json`; adapter reads only validated staged data and the selected source/evidence snapshot.
- Managed classes/support: `.lekalo/generated/php-laravel/operations/`, default namespace `Lekalo\Generated\Operations`; lowercase snake_case paths such as `planner/focus_task/handler.php`, cased PHP FQNs. Deterministic classmap bridges paths to names without running Composer.
- Scaffold source: the closed constant `app/lekalo-operations`, default namespace `App\LekaloOperations`. Recognize it in core lifecycle classification and adapter scopes before permitting writes. A configurable arbitrary root is unsafe with current path-based lifecycle logic.
- Checked observation: `.lekalo/import/observed/operations-evidence.json`, separate from type evidence and scenario run records; final diagnostic/verification evidence must have a consuming core join, not just a JSON file.

**Proposed map shape:** identity/version, project, adapter/version/artifact digest, input/IR/type-map/attachments/profile/lock digests; ID-sorted operation entries with kind/mode, entrypoint FQN/method/path, input/result/error roles, dependency ports, policy/actor/scope mapping, transaction and declared effects, container bindings and scenario operation references; complete path-sorted artifact inventory with role, lifecycle, owner and content digest. Output order is canonical; preserve declared behavioral order inside recipes. Define digests without self-reference: the map's own file digest belongs to the ownership receipt, not inside its hashed content.

Source-map files remain separate `declarations[{id,start,end}]` documents for actual generated PHP byte ranges. `generate.rs::source_map_binding_for` distinguishes them by `declarations`, not the `.map.json` suffix; `module_path_of` probes PHP siblings. Test declaration maps against the staged PHP artifact and input revision. Maintained classes receive observed locations/fingerprints, never generated ranges. Helpers have role plus owning operation, not fabricated semantic definitions.

Four implementation modes with three ownership lifecycles:

1. **Managed:** full generated handler only for accepted recipe semantics; all checks finish before files/manifest publish. Drift blocks overwrite; normal scoped clean can remove owned generated operations while retaining migrations and unrelated artifacts.
2. **Scaffold-once:** emit signature, injected ports and explicit unimplemented failure once. Thereafter body is maintained, including edits/deletion. Re-generation/clean must not replace it. Initial pre-existing unowned file refuses; missing/corrupt marker does not grant ownership. Missing maintained file becomes a verification finding. The scaffold stub is not a passing scenario implementation.
3. **Checked:** no handler/source writes. Declared ID/FQN/method/path joins independently observed current method shape and effects. Required evidence absent, stale, ambiguous or partial cannot pass. Support artifacts may be separately managed only when explicitly requested; a pure checked run produces no replacement.
4. **Custom:** maintained body with explicit contracted signature/dependencies and known versus unresolved effects. A generated boundary wrapper is optional and separately owned. Custom means no business-body rewriting, not exemption from policy/effect/scenario checks; unsupported proofs remain visible.

Register proposed `generate.operations` and `verify.operations` in `target_protocol/capability.rs`, descriptors, profiles and tests. Generation starts `partial` for bounded recipes and reports per-operation coverage; verify requires current shape, binding and effect coverage and does not imply scenario execution. `verify.scenarios` remains separate. Update `build.php`, the bundled `adapter.php` and `scripts/regen-php-adapter-manifest.mjs` output; never edit bundle bytes manually. Add narrowly selected read scopes for operations input and maintained source, not blanket write permission to `app/**`.

## 4. Observed-shape checking, Mago and php -n

Existing `type-bindings.php::{php_check_type_bindings,php_types_check_binding_record}` supplies the missing/ambiguous/stale identity-join pattern. It is not complete handler verification: it compares kind/FQN/path, source digest and selected property names/enum values; it does not prove method parameter/return types, constructor injection, policy or effect behavior. `php_validate_types_evidence` also checks fewer constraints than the JSON schema. Reuse the architecture, not its incomplete checks as a strict acceptance predicate.

Proposed operations evidence requires schema/identity, producer receipt reference/digest, tool/decoder/config/stub/Composer-lock digests, IR/input/type-map/profile digests, complete source inventory and per-operation records. Each record carries semantic ID, native FQN/method, case-preserving relative source path, source digest/range, constructor slots with resolved types, public operation method shape (ordered parameters, required/default/nullability, by-reference/variadic/static/visibility, return), dependency bindings, effect references, unresolved edges and explicit predicate coverage/status. Bound file size, nesting and record counts; duplicate keys/unknown nested fields and overflows refuse rather than truncate.

Join declared authority to observed facts, then to `contracted::{parse_declaration_bytes,check}` and `effects::attach_detected`; compare signature compatibility through normalized type identities, not signature-hash equality alone. Rehash every relevant source/config/binding input before acceptance. Missing inheritance/trait/vendor resolution makes its predicate unknown. A self-authored sidecar with plausible digests is not trusted Mago execution evidence: the controlled producer receipt and its input inventory must be validated. Never load application PHP or boot providers to discover bindings during compilation.

Existing `analyzer.php::MagoEvidenceAnalyzer` consumes `.lekalo/import/mago/receipt.json` and distinguishes unavailable/incompatible/failed/ok; the PHP compiler launches no tools. `mago_decode_symbol` accepts a signature digest, not a full method shape, and relation rows are not a complete transitive call graph. The inspected tree has no `src/provider_evidence/` core runner proposed by old #55 research. Add the needed controlled producer/ingest seam explicitly, initially exercised in the fixture harness; do not imply it already exists in production.

`mago-toolchain.lock.json` pins Mago 1.0.0 and checksums, reports partial references/type inference, and records `ast --json <FILE>` as a command that creates a cache and is not used by the adapter. Qualify that exact pin's public AST/name output with recorded fixtures before implementing AST predicates. If resolved facts cannot be obtained, return unsupported; no regex parser, internal Mago crate dependency or invented upstream rule. Current Context7 documentation confirms structural/perimeter Guard and lint rule listing, not complete application effect inference: [Mago Guard](https://github.com/carthage-software/mago/blob/main/docs/content/en/tools/guard/command-reference.md), [linter](https://github.com/carthage-software/mago/blob/main/docs/content/en/tools/linter/command-reference.md). Local lock/recordings remain the compatibility authority.

`strict-profile.php` currently leaves service-locator, magic-state and explicit-types predicates unsupported. Its final/readonly predicate is a modifier approximation; lint diagnostics matching a rule are used as coverage, so empty diagnostics do not prove that every rule ran. Extend a versioned receipt with explicit executed-rule/predicate coverage and typed AST facts. New operation evidence must not silently widen the old closed Mago receipt; version decoders/producers/fixtures together if its shape changes. Maintain separate declaration, observed and runtime evidence.

Required future lanes: compiler build/protocol/map/emission/custody under `php -n`, using core JSON/hash/string/PCRE facilities and no Composer/vendor, tokenizer extension, mbstring/ctype assumption, application boot, network or children. Syntax-check and load portable emitted classes under `php -n` with an explicit classmap; Laravel wrappers are syntax-checked there but loaded in the provisioned Laravel lane. Use pinned Mago lint/analyze/guard with all generated and checked classes plus approved dependency stubs in a disposable, bounded tool workspace; tool cache writes stay there. Fake evidence tests prove refusal handling only. Required real-tool absence must fail, not skip or become an empty pass.

Existing comparison states are matched, declared-only, detected-only, action-mismatch, scope-mismatch, stale-evidence, unknown-evidence, unsupported-capability and conflicting-evidence. Keep those distinctions and occurrence/resource identities; set equality on a list of entity names loses action, scope and provenance. Attach query/extended-effect/transaction semantics through their owning validated contracts.

Proposed detector follows known calls from the selected entrypoint through injected ports and resolved implementations, including inherited/trait methods and explicit Laravel registrations. Port methods carry declared effect summaries tied to their implementation evidence. A resolved repository write reached by a query produces a blocking proposed `php-operations.query-write` finding, even if a target manifest tries to label it read-only. Also reject query dispatch/external/cache mutations outside its allowed query contract; do not hide them as incidental framework behavior.

Portable core facade aliases/FQNs, `app()`/container lookups and magic dispatch receive proposed `php-operations.hidden-effect` or boundary findings. A Laravel bridge may use framework facilities only under declared boundary metadata; permission to use a facade there does not excuse undeclared effects. Inspect reachable Eloquent observer registration (`observe`, attributes, boot hooks), model-event mappings and event listeners. Known observer writes/emissions contribute transitive detected effects and source spans. Dynamic registration, macros, string-callable indirection or missing vendor facts produce `effect-unknown`, never a purity claim. Recognizing a facade is not itself proof that its call writes.

Register proposed operation rules in the diagnostic registry/profile with bounded reason tokens, semantic ID and logical source range; retain original Mago codes in provider metadata rather than fabricated provider diagnostics. Detection must not execute code. Runtime instrumentation of repository/event/job adapters complements static evidence for executed paths but cannot prove all-path purity. A declared effect absent from one conditional runtime path is not automatically a bug; declared-only and missing analysis coverage must remain distinguishable.

Adversarial fixtures: direct query save; write through injected interface; aliased facade; observer dispatch after a repository save; read-only query; unresolved dynamic call; declared update versus observed create; entity versus field scope mismatch; stale implementation and stale container binding; two competing implementations; no evidence; foreign maintained dependency. Positive/negative real Mago output plus Lekalo reconciliation must traverse the same ingest path as checked acceptance.

## 6. Transaction, policy and dispatch semantics

Transaction port owns one explicitly bound Laravel connection and declares required/optional/forbidden mode, isolation, effect groups, nesting policy and retry budget. Required local atomicity includes every repository write and any durable idempotency/outbox row in the same connection/transaction. No facade in the portable handler; framework wrapper injects the connection/transaction adapter. Refuse unsupported isolation, multiple-store atomic groups and nesting guarantees instead of substituting Laravel defaults. Atomic groups alone do not guarantee one-focused-task concurrency: require the declared storage constraint/locking or CAS and two-connection PostgreSQL proof where claimed.

Laravel commits a normally returned closure result and rolls back/rethrows on exceptions; deadlock attempts may rerun the closure. [Laravel 13 transactions](https://github.com/laravel/docs/blob/13.x/database.md). Therefore **proposed wrapper rule:** convert a typed domain failure inside the transaction into a private rollback signal, catch only that signal outside the completed rollback and return its domain result. Unexpected throwables remain infrastructure failures. Alternatively use explicitly owned begin/commit/rollback with equally tested behavior; do not return `Result::error` inside `transaction()` and accidentally commit earlier writes. An error after commit cannot be relabeled as a rolled-back failure.

Default retry attempts to one. Enable additional attempts only when #24/#62 declarations and port effects prove replay safety; rebuild attempt-local buffers. A key name alone is insufficient. Durable idempotency binds actor/scope, operation and canonical request digest; same key/different request is conflict, same request replays the committed result without duplicate writes/events. Existing PlannerPort's in-memory cache is not crash/concurrency proof. Post-commit unknown and external partial failures require the declared reconciliation/compensation boundary, never blind retry.

Policy is an injected port taking explicit actor, operation input and resource scope. Bind Laravel authenticated principal/guard to the declared actor type; user IDs in request payload never become trusted authority. Enforce required actor/scope presence, tenant/workspace/user dimensions, deny dominance and resource identity. For state-dependent policy, read and authorize the relevant locked/snapshot resource inside the transaction before mutation; prevent check/use races. Query repositories must receive and enforce the same scope. No ambient Auth facade/global current-user lookup in portable code, no implicit internal/system bypass. Request-scoped actor services must not leak between queue jobs or long-lived workers. Container interface injection is supported by [Laravel 13 container](https://github.com/laravel/docs/blob/13.x/container.md); exact target bindings remain explicit project metadata.

Event/job ports take #58 payload types and declared semantic IDs. Buffer local notifications until the successful outer commit; drop them on rollback. Laravel `after_commit`/`afterCommit()` delays queue dispatch until parent transactions commit and discards rollback dispatches. [Laravel 13 queues](https://github.com/laravel/docs/blob/13.x/queues.md). This is not a durable database-to-broker atomicity guarantee: the proposed durable mode requires a transactional outbox plus idempotent delivery, or explicit unsupported. Test nested transactions and post-commit delivery failure separately; a local rollback cannot unsend external I/O. [Laravel observers](https://github.com/laravel/docs/blob/13.x/eloquent.md) can defer via `ShouldHandleEventsAfterCommit`, but such an observer remains a declared/detected effect, not hidden domain logic.

Keep deterministic clock/ID ports when semantics need them. Preserve public/private error payload policy and avoid raw SQL, exception text, host paths or credentials in neutral evidence. These decisions are design requirements inferred from the documented transaction/dispatch behavior, not results of a runtime test in this research.

## 7. Scenario entrypoint and locally understandable target structure

Existing call chain: `scenario-map.php` validates operation references; `scenario-emit.php` emits `Port::instance()->invoke(...)`; its port shim resolves `lekalo/php-test-port.json`; `tests/fixtures/php-laravel/planner/tests/Support/PlannerPort.php` dispatches focus through the HTTP kernel; `app/Http/Controllers/TaskFocusController.php::focus` currently reads/saves Eloquent and emits an event. The missing-task branch and idempotency are partly in the port; it appends its own effect/emission log after HTTP success. This is an executable fixture seam, not proof of a generated/checked handler or independently observed effect correctness.

Proposed fixture change: thin controller decodes transport, binds actor, calls the selected operation entrypoint and encodes result. PlannerPort invokes that same entrypoint directly or through the real HTTP route, with a declared mode and no substitute business path. Missing task, policy denial and idempotency must traverse it too. Replace synthetic effect bookkeeping with captures from actual repository/event/job ports (plus database state assertions). Tamper handler result, bypass policy, remove transaction, add an observer or duplicate dispatch: corresponding scenarios must fail. Test both a generated bounded handler and a checked maintained handler against the same semantic corpus.

Keep source organization per module/operation: entrypoint, narrow interfaces and a compact operation map explaining input/result/errors, actor/policy, transaction, declared effects, concrete dependency bindings, ownership and tests. Shared types remain linked by #58 IDs. Avoid a monolithic generated file or runtime registration magic; a reviewer should follow one handler plus its explicit dependency map to maintained implementations. Proposed small-context gate: a fixture check resolves all those references for focus from its local manifest and opens no unrelated operation bodies; snapshot the bounded operation summary, and reject dangling/ambiguous links. File-count/size bounds are usability constraints, not claims about AI comprehension.

Scenario records retain existing neutral outcomes and contract; attach validated entrypoint/source/operations-map fingerprints through a versioned sidecar/consumer join if current run evidence cannot carry them. Do not stuff new fields into scenario-run v0.4.0. Trace connects semantic operation, PHP entrypoint, executed test and gate with current digests. Checked test ownership and checked handler ownership are independent. A passed old test or HTTP 200 cannot replace complete expected assertion inventory and terminal execution evidence.
